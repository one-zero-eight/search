# Деплой cAtIx для бета-теста

Один сервер (VPS/VM) с Docker. Модели (llama.cpp) остаются на GPU-сервере: приложение ходит к ним по сети или через SSH-туннель.

## 1. Что нужно
- Linux-сервер с Docker и Docker Compose v2, 2 ГБ ОЗУ и 10 ГБ диска хватит на бету.
- Доступ с сервера к llama.cpp серверам: чат `:8080`, эмбеддинги `:8081`, реранкер `:8082` (напрямую или через профиль `tunnel`).
- Отдельный бот у @BotFather для беты (privacy mode выключен: `/setprivacy` → Disable); пользовательское меню содержит `/start`, административные команды скрыты даже для админов.
- Отдельный Telegram-аккаунт для userbot (не личный): он читает чаты, куда вступил.

## 2. Первый запуск
```bash
git clone <репозиторий> && cd cAtIx
cp .env.example .env          # заполнить; пароли: openssl rand -base64 24
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml ps
```
Поднимутся `db`, `redis`, `migrate` (схема БД, повторяемо), `wiki` (вики в базу из checkout ветки `wiki`, см. 2a), `mcp`, `tgbot`, `userbot`, `maxuserbot`, `worker`, `api`, `phoenix` (трейсы, раздел 6a). Оба userbot включены по умолчанию, без профилей; перед чтением чатов нужен однократный интерактивный вход в соответствующий аккаунт (раздел 4). Логи: `docker compose -f docker-compose.prod.yml logs -f tgbot`.

`mcp` — отдельный HTTP-сервер инструментов. Он собирает каталог при старте, доступен приложениям как `http://mcp:8010/mcp` и не публикует порт наружу. API и боты ждут его `/health`. Подтверждения выполняет клиент cAtIx по списку имён инструментов; сервер проверяет пользовательские credentials и аргументы, но не требует билетов или Redis для согласия. Другой клиент с действительными credentials может вызвать изменение напрямую. Для обновления инструментов перезапускайте также `mcp`; при изменении клиентского списка подтверждений — приложения. Логи: `docker compose -f docker-compose.prod.yml logs -f mcp`. Локально вне Docker сервер запускается командой `uv run catix-mcp` на `127.0.0.1:8010`, а `scripts/catix.sh up` управляет им вместе с приложениями.

Проверка: Telegram-бот отвечает на `/start`, в логе `tgbot` строка `Running as @...`. `/start` включает получение существующих уведомлений об изменениях расписания; учебную группу пользователь настраивает на сайте. При запуске бот обновляет меню, убирая старые пользовательские и административные команды, в том числе из администраторских меню. Авторизованные администраторы по-прежнему вызывают операции вручную; `/id` доступна только им.

Сайт — единственный пользовательский интерфейс ассистента и личного календаря; CLI остаётся для диагностики. Telegram-бот и пользовательские аккаунты Telegram/MAX собирают сообщения настроенных источников, но не запускают агента для личных сообщений, упоминаний, ответов или inline-запросов. Telegram сохраняет календарные уведомления; MAX userbot ничего не отправляет и полностью игнорирует личные диалоги и команды. Агент сайта, MCP и извлечение изменений расписания продолжают работать.

## 2a. Вики документов (поиск по положениям, правилам приёма, курсам)
Вики живёт не в коде, а в своей ветке `wiki` (orphan: только `wiki/` и `raw/`). В неё коммитит только сама вики (раздел 2b), и только то, что прошло проверки. На сервере рядом с кодом лежит checkout этой ветки, сервис `wiki` читает его и кладёт в базу только изменившиеся страницы:
```bash
git clone -b wiki --single-branch <репозиторий> ../catix-wiki      # один раз; другой путь — WIKI_DIR в .env
docker compose -f docker-compose.prod.yml run --rm wiki              # первый раз: ~20 с, 2155 файлов
```
Векторы не обязательно считать на сервере заново: индекс можно привезти с машины, где он уже посчитан. Это только вики-таблицы, сообщения чатов не затрагиваются; импорт занимает около 2 минут против ≈45 на подсчёт. Файл около 370 МБ, в git его не кладём:
```bash
uv run catix-wiki index export wiki-index.tar.gz                        # локально; в файле записан коммит ветки wiki
scp wiki-index.tar.gz server:/srv/cAtIx/
docker compose -f docker-compose.prod.yml run --rm -v ./wiki-index.tar.gz:/tmp/wiki-index.tar.gz:ro wiki catix-wiki index import /tmp/wiki-index.tar.gz
```
После импорта сервис `wiki` досчитывает только то, что изменилось после коммита из файла.

`api` и `worker` монтируют тот же checkout только для чтения (`WIKI_ROOT=/wiki-data`): код вики без `WIKI_ROOT` не запускается, а писать в вики может только её собственный прогон.

Просмотр процитированных PDF внутри ZIP/7z скачивает архив при первом открытии и извлекает
конкретный файл через ограниченный распаковщик. API берёт путь и полный SHA-256 из существующих
метаданных `raw/rpd/index.json` или манифеста `*.archive.json`, сверяя их с идентификатором
источника в странице и её версией в индексе. Для этой функции не нужны отдельные `regs compile`,
`rpd compile`, переиндексация или доставка исходных PDF на сервер; checkout wiki и индекс
должны, как обычно, соответствовать друг другу. LLM, OCR и конвертация документов не запускаются.

Архивы и проверенные PDF сохраняются в `ARCHIVE_PREVIEW_CACHE` (по умолчанию
`data/archive-previews`, внутри уже подключённого `catix_data`), не в read-only `WIKI_ROOT`.
Каталог должен быть доступен API для записи. Кэш ограничен 512 МиБ; неиспользуемые сутки файлы
удаляются при следующем обращении. Одновременные открытия используют общий кэш и блокировку;
повторное открытие PDF не требует ни сети, ни распаковки. Отсутствующая или изменившаяся редакция
даёт 404, сбой скачивания/распаковки — 502, недоступный каталог кэша — 503, таймаут — 504.
Первое открытие требует доступа API к сайту источника. Старые сохранённые ответы без метаданных
просмотра сохраняют исходную ссылку на архив.

Новые коммиты вики привозит `scripts/wiki-pull.sh`: `git pull` ветки и, если что-то пришло, сервис `wiki`. Скрипт ставится в cron, например `*/15 * * * * /srv/cAtIx/scripts/wiki-pull.sh >> /var/log/catix-wiki-pull.log 2>&1`. Пересобирать образ для обновления вики не нужно.

Векторы кусков считает `worker` в фоне, когда нет новых сообщений из чатов. Пока векторов нет, куски находятся по словам. Первый раз это займёт около 45 минут (88 тыс. кусков), дальше — секунды на коммит. Очередь вики в алертах не участвует.

Проверка:
```bash
docker compose -f docker-compose.prod.yml exec worker catix-wiki index status   # страницы, куски, векторы, очередь
```
Для поиска нужен и реранкер (`RERANKER_ROUTE`): без него поиск работает, но заметно хуже (80% против 90% в первой пятёрке). Если сменить `EMBEDDINGS_MODEL`, все векторы вики пересчитаются сами.

## 2b. Вики обслуживает себя сама (машина с локальной LLM)
Каталог источников — данные вики: `WIKI_ROOT/raw/sites.yaml` хранит одобренные сайты и `blocked`,
`WIKI_ROOT/raw/sites-discovered.json` — кандидатов с полями `name`, `config`, результатами проверки и статусом.
`sites approve HOST_OR_NAME` (и `sites accept`) переносит настройки в каталог этого же checkout,
скачивает HTML-страницы выбранного сайта (у доверенных сайтов, на которые он ссылается, — только страницы, которых
в вики ещё нет; известные перечитывает еженедельный обход), собирает `wiki/raw/sites/` и обновляет навигацию `index.md`.
Агент вики, остальные источники, скачивание PDF/DOC и индекс PostgreSQL этим действием не запускаются.
Если скачивание или сборка не удались, команда завершается ошибкой, но одобрение сохраняется;
тот же `sites approve HOST_OR_NAME` можно повторить для уже одобренного сайта. Параллельный запуск
блокируется общей `.autopilot.lock`. `--all` относится только к ожидающим одобрения сайтам.
`autopilot accept` также одобряет и собирает pending-сайты перед коммитом каталога вместе со страницами;
git-откат восстанавливает оба. Установленный Python-пакет ни одна из этих операций не меняет.
Файл перечитывается при изменении, перезапуск процесса после approval не нужен.

При обновлении старой установки сначала сохраните её `src/catix/wiki/sources/sites.yaml`, затем выполните
миграцию новым кодом (без обхода сайтов и без запуска агента), когда обновление вики не работает:
```bash
WIKI_ROOT=/path/to/wiki-checkout uv run catix-wiki sites migrate --from /path/to/saved/sites.yaml
```
Если `raw/sites.yaml` уже есть, старая копия его не перезаписывает. Настройки из старого
`raw/sites-pending.yaml` переезжают в `config` записей JSON, а оригинал сохраняется как `.yaml.bak`.
Повторный запуск ничего не меняет. В новой установке каталог приходит с checkout ветки `wiki`;
его отсутствие — ошибка с подсказкой миграции, а не повод молча использовать каталог из кода.
Одобрение и миграцию выполняйте без параллельной записи других команд в тот же checkout.

HTML-обход использует только явно заданный `base` сайта и его `aliases`. Алиас — другое имя того же
сайта: запрос идёт на основной хост с тем же путём, кеш и ссылки в вики общие. Отдельная запись
поддомена имеет собственные настройки, ограничения и каталог кеша; её основной хост важнее алиаса
в чужой записи. Неизвестный поддомен не наследует HTML-обход родителя: он проходит обычные
`sites discover` / `sites review` / `sites approve`. Для документов доверие к поддоменам одобренного
поставщика сохраняется отдельно. `blocked`, pending-статус и исключения путей не снимаются алиасом.

`catix-wiki autopilot --loop` работает там, где есть LLM (llama.cpp), и пишет в checkout ветки `wiki` (`WIKI_ROOT` в `.env`, обязателен: без него, как и с `WIKI_ROOT` на checkout кода, команды вики не запускаются):
```bash
git worktree add ../catix-wiki wiki          # или git clone -b wiki; затем WIKI_ROOT=<путь> в .env
uv run catix-wiki autopilot --loop           # лучше как systemd-сервис пользователя
```
- **Источники** (`src/catix/wiki/sources/`, расписание в `__init__.py`) опрашиваются по своему расписанию:
  - `eduwiki` — каждые 6 часов, по номерам ревизий;
  - `new-pages` — каждые 6 часов: ленты и новые страницы сайтов через `fetch_new` (среди лент университета — раздел сведений `sveden/`, обычные страницы сайта), документы только по текстовому слою, новые архивы РПД; сохранённые ссылки на документы проверяются и при неизменившихся страницах, поэтому `sites approve` делает доступными ссылки со старых страниц без их повторного обхода;
  - `sites` — раз в неделю: полный обход сайтов через `fetch`, включая документы и ссылки из них, без OCR;
  - `files` — раз в неделю: HEAD каждого прочитанного документа (ETag, дата, размер), изменившиеся скачиваются заново.

  `catix-wiki autopilot --source new-pages` спрашивает источник сразу, `catix-wiki autopilot --site hotel --site campuslife` читает источником `sites` только эти сайты, а расписание полного обхода при этом не сдвигается.
- **Заявки API.** `POST /{section}/parse` ничего не читает и в вики не пишет. Он ставит заявку в Redis (`src/catix/wiki/parse_requests.py`, ключи `ctx:wiki:parse:*`), а autopilot выполняет её в ближайшем прогоне вместе с источниками по расписанию, с теми же проверками и коммитом. Результат пишется обратно в заявку (`GET /parse/{id}`). Поэтому `REDIS_URL` у autopilot должен указывать на тот же Redis, что у сервиса `api`. Без `REDIS_URL` autopilot заявок не берёт, а API отвечает `503`. Если autopilot работает на другой машине, опубликуйте порт Redis только на `127.0.0.1` сервера (`ports: ["127.0.0.1:6379:6379"]` у `redis` в `docker-compose.prod.yml`) и ходите к нему через SSH-туннель, например `ssh -N -L 6381:127.0.0.1:6379 server` и `REDIS_URL=redis://localhost:6381/0`. Пароля у Redis нет, наружу его не открывайте. `--loop` проверяет очередь каждые 30 секунд. Заявки, которые пришли во время прогона, ждут его конца.
- **PDF** читает opendataloader-pdf (`src/catix/wiki/sources/opendataloader.py`, без моделей). Ему нужна Java 11+ на этой машине (`java -version`). Он восстанавливает порядок чтения колонок, не путает рамку вокруг текста с таблицей, понимает таблицы с объединёнными ячейками. Колонтитул попадает в текст один раз, где впервые встретился («Приложение 2 к Положению…»), а номера страниц не попадают. Слово, разорванное переносом, склеивается по словам документов: «консорциума», но «научно-технической». Если Java нет или он прочитал слишком мало, PDF читает pdfplumber.
- **Очередь OCR.** Источники `new-pages`, `files`, `sites`, а также `sites fetch` и `sites explore` читают документы по текстовому слою. Сканы сохраняются в очереди (`"ocr": "queued"` в `.json` документа), без повторной загрузки и извлечения текстового слоя на следующих прогонах. Ночного окна и автоматического переключения GPU нет: бот не отдаёт свою LLM под OCR, а мониторинг моделей работает круглосуточно. Пока нет отдельного OCR-сервера, очередь может просто ждать.
  Вручную: `catix-wiki regs fetch` читает документы и накопленные сканы с OCR; `catix-wiki regs fetch --no-ocr` только пополняет очередь и читает текстовые слои. Сканы читает только chandra-ocr-2 (`src/catix/wiki/sources/chandra.py`, `OCR_ROUTE`, по умолчанию `http://localhost:8082/v1`, `OCR_MODEL=chandra`). Если сервер недоступен, страница не прочитана или ответ пуст, скан остаётся в очереди независимо от числа попыток. Другого OCR нет. `OCR_PARALLEL` задаёт число одновременно читаемых страниц и сканов: страницы всех сканов идут в общую очередь. За прогон читается до 200 страниц OCR (`OCR_BUDGET` в `regulations.py`), остаток остаётся в очереди. Сканы длиннее 40 страниц (`MAX_OCR_PAGES` в `regulations.py`; у экзаменов — 20, `MAX_SCAN_PAGES` в `pastpapers.py`) в очередь не ставятся: они откладываются отдельно (`"ocr": "too long"`), и ни один прогон их не читает, не скачивает заново и не спрашивает их текстовый слой. Если поднять лимит, они сами возвращаются в очередь; файл, изменившийся на сайте (`regs refresh`), смотрится заново. Очередь (по источникам: документы и экзамены, с числом страниц, датой и неудачными попытками chandra) и отдельно отложенные сканы показывает `catix-wiki regs queue`. Когда очередь или список отложенных растёт, `autopilot` пишет админам в Telegram (`TG_BOT_TOKEN`, `ADMIN_TELEGRAM_IDS` и админы из бота): о каждом новом скане один раз, со списком новых и командой, которая их прочитает; что уже сказано, хранится в `.autopilot.json` (`ocr_told`). Экзаменационные материалы (`papers`) по расписанию также читаются без OCR; их сканы хранятся в `raw/past-papers/index.json` и читаются вручную командой `catix-wiki papers fetch`, только через chandra. После смены способа чтения запускаются `catix-wiki regs reextract && catix-wiki regs compile && catix-wiki index`, а заранее сравнить старое и новое чтение можно так: `uv run python experiments/compare_extraction.py` (какие пункты сохранятся, сколько слов).
- **Архивы ZIP/7z.** Ссылки из страниц и документов поступают в общий обработчик `regulations`: каждый PDF/DOC/DOCX/RTF внутри становится отдельным документом, скан — записью в существующей очереди OCR. В цитате сохраняются настоящий URL архива и путь файла внутри (`archive_member`); HTTP-ссылка на внутренний файл не придумывается. Для ссылок `/download?id=…`, `/download.php?…` и `/file?…` формат определяется по Content-Type ответа HEAD, параметры сохраняются. Остальные адреса без расширения пока автоматически не классифицируются. Фактический формат проверяется по содержимому; DOCX не раскрывается как набор документов.
  Распаковщик — `libarchive-c` и системная `libarchive` (`libarchive13` в Debian/Docker, `libarchive` в Arch). Он работает отдельным процессом: до 100 MiB загрузки, 1000 записей, 100 MiB на файл и 500 MiB суммарной распаковки; до 60 секунд на распаковку, 512 MiB адресного пространства. Выход за каталог, ссылки и специальные файлы запрещены; имена файлов на диске генерируются кодом. Вложенные архивы и неподдерживаемые файлы отмечаются в списке содержимого, но не раскрываются. Пароль, повреждение и превышение лимита сохраняются как явные ошибки.
  Если URL архива на самом деле отдаёт PDF, формат определяется по содержимому и проверяется `pdfinfo`: файл передаётся обычному читателю документов, без распаковки и без выдуманного `archive_member`. Исходный URL и ключ сохраняются; скан попадает в ту же очередь OCR. Это работает и для прежнего результата `unsupported`: новый fetch повторяет попытку. Успешно распознанные PDF хранятся в `<key>.documents/<sha256>/`; повторный прогон не скачивает и не извлекает их заново, а `regs refresh` проверяет исходный URL. Ошибочный ответ не заменяет предыдущую версию; переход между настоящим архивом и одиночным PDF публикуется компилятором после успешного чтения контейнера/файла.
  Рядом с документами находятся `<key>.archive.json` (последний успешно прочитанный состав и состояние попытки), `<key>.archives/` (исходники) и `<key>.members/` (версии файлов, их текст и очередь OCR). Неизменившиеся файлы не перечитываются, утраченный локальный файл восстанавливается из сохранённого архива. `regs refresh` проверяет контейнер один раз, а не по числу файлов. Новый состав публикуется только после полной успешной распаковки; неудачная замена сохраняет предыдущие документы. Удалённые файлы исчезают из страниц при `regs compile`, затем из поиска при обычной синхронизации индекса. Старые локальные версии пока сохраняются, автоматической очистки нет. Архивы РПД используют тот же безопасный распаковщик, но сохраняют свой компилятор дисциплин и не дублируются общим обработчиком.
- **Пересборка.** Если что-то пришло: страницы, связи, индекс.
- **Проверки:**
  - lint без ошибок;
  - поиск находит ответы `src/catix/wiki/quality.py` (hit@5 ≥ `WIKI_MIN_HIT5`, по умолчанию 80%);
  - агент проходит `tests/test_docs_answers.py` (упавший тест запускается ещё раз). Тесты запускаются через `python -m pytest` того же окружения, что и автопилот, поэтому `.venv` нужен с dev-зависимостями (`uv sync`). Если pytest не запустился или тесты пропущены, потому что сервер модели не ответил, проверка тоже не проходит: ответы не проверены, и в строке проверки так и написано, с причиной; вывод pytest попадает в лог прогона.
- **Коммит.** Все проверки прошли — коммит от «cAtIx wiki» в `wiki` и push. Что-то не прошло — те же изменения уходят в ветку `wiki-review/<время>`, а `wiki` не меняется. Человек смотрит и решает: `catix-wiki autopilot accept` (в `wiki` и push) или `catix-wiki autopilot discard`.
- **Модель вики.** Вики пишет код: `wiki/raw/` — документы (положения, РПД, eduwiki, сайты) как их публикуют источники (`src/catix/wiki/paths.py`). Модель вызывается только в двух местах: перевод страниц eduwiki в markdown (`compile.py`) и выбор курса для строки пререквизита, которую не нашло сравнение строк (`graph.py`, ответы кэшируются). Документы раздела сведений модель не отбирает: это страницы сайта, их документы читаются как документы любого сайта. Её можно взять отдельно: `WIKI_LLM_ROUTE`, `WIKI_LLM_MODEL`, `WIKI_LLM_API_KEY` (туда уходят только публичные документы университета). Трейсы `catix-wiki` идут в отдельный проект Phoenix `catix-wiki`.
- **Защита путей.** Коммит, затронувший что-то кроме `wiki/` и `raw/`, не делается вовсе. На GitHub стоит включить защиту ветки `main`, а токену машины с вики дать права только на `wiki` и `wiki-review/*`.

## 2c. Модели на той же машине
Если llama-серверы запущены на той же машине, что и Docker, контейнеры не могут ходить на `localhost`: это сам контейнер.
- **Обычный Docker:** `LLM_ROUTE=http://host.docker.internal:8080/v1` (и так же 8081, 8082). Имя уже прописано в `docker-compose.prod.yml` (`extra_hosts`). llama-серверы должны слушать не только 127.0.0.1 (`--host 0.0.0.0` или адрес `docker0`).
- **Rootless Docker** (`docker info` показывает `rootless`): `host.docker.internal` (172.17.0.1) ведёт в сеть rootlesskit, а не на хост, и даёт `Connection refused`. Нужен IP машины в локальной сети (`ip -4 addr`, интерфейс вроде `eth0`), например `LLM_ROUTE=http://10.1.1.27:8080/v1`; llama-серверы с `--host 0.0.0.0`.

Проверка из контейнера (после правки `.env` — `docker compose -f docker-compose.prod.yml up -d --force-recreate tgbot worker`):
```bash
docker compose -f docker-compose.prod.yml exec worker python -c "import httpx; print([httpx.get(f'http://10.1.1.27:{p}/health').text for p in (8080, 8081, 8082)])"
```

## 3. Модели через SSH-туннель (если GPU-сервер напрямую недоступен)
Положить в `secrets/ssh/` ключ `id_ed25519` (chmod 600) и `known_hosts` GPU-сервера, в `.env`:
```
GPU_SSH=user@gpu-host
LLM_ROUTE=http://tunnel:8080/v1
EMBEDDINGS_ROUTE=http://tunnel:8081/v1
RERANKER_ROUTE=http://tunnel:8082/v1
```
```bash
docker compose -f docker-compose.prod.yml --profile tunnel up -d
```

## 4. Userbot (чтение чатов аккаунтом)
Userbot запускается по умолчанию вместе с остальными сервисами. Перед первым запуском выполните интерактивный вход (код из Telegram); он делается один раз, сессия хранится в томе `catix_data`:
```bash
docker compose -f docker-compose.prod.yml run --rm userbot catix-tguserbot login
docker compose -f docker-compose.prod.yml up -d userbot
```
Настройка — в личном чате с Telegram-ботом: авторизованный администратор вручную вводит `/admin` → «Группы и источники» или «Администраторы».
`/listen` остаётся ручным быстрым входом в группы. Административных команд нет в меню даже у админов; `/id` доступна только им. Новый администратор должен один раз написать боту `/start`.

### MAX: переключение с официального бота на пользовательский аккаунт

Порядок для оператора (не автоматическая регистрация):

1. **Сначала остановите прежний `maxbot`** средствами старой установки: например,
   `docker compose -f docker-compose.prod.yml --profile maxbot stop maxbot`
   со старым Compose-файлом, до его замены. Новый launcher старый процесс не обслуживает.
2. Обновите код и образ, примените схему новым кодом: `uv run catix-db init`,
   либо `docker compose -f docker-compose.prod.yml run --rm migrate`.
   Сообщения и OCR старого источника не удаляются. Непустые таблицы незавершённой
   Bot API state-схемы блокируют миграцию: не очищайте их автоматически.
3. В интерактивном TTY выполните QR-вход разрешённым аккаунтом. Compose запускает
   `maxuserbot` по умолчанию; перед входом остановите listener, чтобы освободить сессию:

   ```bash
   uv run catix-maxuserbot login
   # либо в общем томе catix_data (не добавляйте -T):
   docker compose -f docker-compose.prod.yml stop maxuserbot
   docker compose -f docker-compose.prod.yml run --rm maxuserbot catix-maxuserbot login
   ```

   QR показывается только в терминале, пароль 2FA вводится через getpass и не хранится.
   `MAX_SESSION=data/max/account.db` — отдельная от Telegram сессия; каталог 0700,
   SQLite и sidecars 0600. Она даёт доступ к полному аккаунту: не включайте её в
   backups, логи и артефакты без явного разрешения. `login --replace` удаляет только
   локальную сессию после подтверждения, не завершает другие сеансы MAX.
4. Пока listener остановлен, проверьте каталог без повторного входа:

   ```bash
   uv run catix-maxuserbot chats
   # либо после Docker login:
   docker compose -f docker-compose.prod.yml run --rm maxuserbot catix-maxuserbot chats
   ```

5. Запустите `listen` и обновлённый Telegram-бот (профиль MAX больше не нужен):

   ```bash
   docker compose -f docker-compose.prod.yml up -d maxuserbot tgbot
   # локально: uv run catix-maxuserbot listen (или scripts/catix.sh up)
   ```

   Локальный launcher читает только путь сессии через Settings и пропускает MAX,
   если файла нет. Compose сервис не пропускает: без сессии `listen` завершается с
   `login_required` и перезапускается согласно restart policy. `chats` и `listen`
   не запускают QR/2FA; при `login_required` оператор останавливает listener и входит
   вручную, затем снова запускает сервис. Одновременно сессией владеет
   одна команда (flock); daemon также держит отдельный advisory lock Postgres.
6. В Telegram `/admin` → «Группы и источники» → «MAX» (или `/listen` → MAX)
   обновите каталог, выберите чат/канал и **явно** задайте аудиторию. Для этого пути
   аккаунт должен уже состоять в чате; права администратора ему не требуются.
   Выберите прежний legacy-источник либо «Нет старого источника», проверьте оба ID,
   число старых сообщений и предупреждение, затем подтвердите сохранение.
   Только первое подтверждённое включение скрывает связанный старый архив из поиска;
   сообщения, OCR и прежняя аудитория остаются в БД. Off не возвращает архив в поиск
   и не удаляет новый контент. Не выбранный legacy-источник не скрывается.

   Альтернативный путь — заявка на Telegram/MAX-источник с сайта с согласием
   администратора чата на выбранную аудиторию. Одобрение модератором cAtIx ставит
   заявку в очередь account worker для автоматического вступления. Это единственное
   разрешённое исключение из пассивного режима MAX; сообщений, read receipts,
   typing и reactions userbot не отправляет. Статус «Одобрено; в очереди на
   подключение» не означает доступ. При ожидании подтверждения доступа
   администратору чата может потребоваться одобрить заявку на вступление.
   Индексация и загрузка истории начинаются только после свежей проверки доступа,
   а не сразу после одобрения модератором. Legacy-архив автоматически не привязывается.
   При таймауте join worker сверяет текущее членство без слепого повторного вступления.

   **При обновлении существующей установки перезапустите MAX worker новым кодом**
   (Compose: `docker compose -f docker-compose.prod.yml up -d --build --force-recreate maxuserbot`).
   Уже одобренные заявки будут обработаны из очереди; ручная правка БД не нужна.
   Этот порядок не означает, что реальное вступление в живой MAX уже проверено.

Новые источники выключены до подтверждения; личные диалоги и комментарии не индексируются.
Сервис `maxuserbot` использует общий env_file/data volume, ждёт миграцию и Redis,
не зависит от MCP и не открывает HTTP endpoint/порты. Используется стандартное TLS
хранилище доверия: не отключайте проверку сертификатов. Не нужны Bot API token,
webhook, scraping браузера или изменение production `.env` автоматическими командами.

PyMax (`maxapi-python` 2.5.0, MIT) закреплён на revision
`c4cb917d354a1179be625925530d72c8aaa969ff`. API неофициальный: возможны изменения
протокола и блокировка аккаунта. При enable/re-enable загружается вся история,
доступная аккаунту через API, без возрастного ограничения. При старте `listen`
для уже включённых источников с ещё не запрошенной историей запускается первая
полная загрузка; незавершённая загрузка продолжается с durable cursor, завершённая
не переигрывается, а остановленные, partial/failed full history не сбрасываются
автоматически. Для повторной полной загрузки используйте «Повторить историю».
Отдельно при каждом подключении восстанавливается разрыв от сохранённого watermark
(без watermark — вся доступная история). Выключенные источники не подключаются
автоматически; аудитория и официальность не меняются. UI отдельно показывает full
history и gap recovery. Timestamp pagination без прогресса даёт partial, а не ложный
успех. Crash до commit нашего inbox может потерять событие; reconnect не гарантирует
восстановление всех offline edits/deletes.

Hermetic-проверки не заменяют live MAX. Реальные QR/2FA, статус доступа ACTIVE,
доставку, поиск/OCR и визуальную Telegram-проверку оператор проверяет на согласованном
тестовом аккаунте. Guarded SQL-тестам нужен явно предоставленный disposable
`IMAGE_QUEUE_TEST_DSN` с БД `catix_image_queue_test`; без него DB integration не выполнена.
Не используйте production credentials для тестов и не выдавайте synthetic transport за live proof.

### Подключение групп и режимы топиков

Перед запуском новой версии примените `db/schema.sql` новым кодом (`catix-db init`,
в Compose — сервис `migrate`), затем обновите `tgbot` и `userbot`. Схема применяется повторно;
существующие настройки сохраняют прежнее поведение. Не оставляйте старый userbot с новой
админкой: он не понимает ограничения поиска по топикам.

В «Группы и источники» видны подключённые чаты. «Добавить группу» открывает доступные
диалоги с поиском по названию/ID. Это выбор чата, к которому userbot или бот уже имеет доступ,
не автоматическое вступление по приглашению. Если чата нет, сначала добавьте туда бот или
аккаунт userbot и обновите список.

Мастер: чат → учебная группа → режимы топиков → проверка → подтверждение.
До подтверждения ни настройки, ни загрузка истории не включаются; отмена отбрасывает черновик.
Добавление Bot API бота в новый чат только делает его доступным для настройки, а не включает хранение.

- **Хранить** — сохранять сообщения для базы знаний (с историей, если читает userbot).
- **Только поиск** — искать в Telegram по запросу, без сохранения новых сообщений и без фоновой обработки.
- **Выключен** — не сохранять новые сообщения и не возвращать топик в поиске Telegram.

Для userbot по умолчанию остальные и новые топики получают «Только поиск»: можно отметить
«Объявления» для хранения, не настраивая каждый топик отдельно. Пустой выбор хранения означает
«ничего не хранить», не «весь чат». Для чатов без топиков выбирается режим всего чата.
Если в чате есть только Bot API бот, поиск Telegram недоступен и списка топиков нет:
можно включить хранение всего чата с момента подключения либо оставить его выключенным.

«Дополнительно» содержит выбор читающего клиента, отметку официального источника и отдельную
очистку сообщений с подтверждением. Смена режима и отключение группы не удаляют старую историю:
уже сохранённые сообщения остаются в базе знаний, пока администратор явно не очистит их.
Настройки подхватываются работающими клиентами в течение очередного опроса.

### Источники в диалоге на сайте

Кнопка «Источники» в верхней панели диалога открывает доступные пользователю Telegram-чаты:
общие незащищённые источники и чаты всех подтверждённых учебных групп. `GET /sources` требует
пользовательский Bearer-токен, заново проверяет группы и возвращает `Cache-Control: private, no-store`.
При недоступной проверке показываются только общие источники; ручная группа не даёт доступа.
Приглашения и административный список обнаруженных, но не подключённых чатов не возвращаются.

Режимы хранения и поиска показаны отдельно для чата и его тем, с учётом выбранного читателя
и известного членства клиентов в чате. Это конфигурация, а не индикатор подключения к Telegram
прямо сейчас. Отключённые источники с сохранёнными сообщениями остаются в списке с отметкой
доступной истории. Панель не является перечнем цитат конкретного ответа.

Для этого раздела дополнительная миграция не нужна поверх схемы политик тем и заявок:
сначала обновите `api`, затем website с типами из нового OpenAPI. Старый API отвечает на
`GET /sources` ошибкой, которую панель показывает явно, а не заменяет пустым списком.

### Заявки пользователей на чаты Telegram и MAX

На сайте cAtIx пользователь предлагает публичный чат или канал по ссылке `t.me/username`
либо приватное приглашение `t.me/+…` или `t.me/joinchat/…`, а также чат/канал MAX
`max.ru/NAME` или `max.ru/join/TOKEN` (с `https://` или без),
выбирает аудиторию «Для моей группы» или «Для всех пользователей
cAtIx» и добавляет комментарий. Он подтверждает, что администратор чата согласовал
индексацию и доступ выбранной аудитории; при смене аудитории или группы согласие сбрасывается.
Это не проверка членства в чате: сообщения смогут видеть и пользователи, не состоящие
в этом чате. По умолчанию выбран групповой режим; общедоступный требуется выбрать явно.
Ссылки на папки, сообщения и служебные действия Telegram этой формой не принимаются.
Ссылки на личные аккаунты и ботов отклоняются при проверке userbot. Публичная ссылка сама
по себе не меняет аудиторию заявки и не отменяет модерацию.

Заявки хранятся в Postgres отдельно от активных источников. Отправка формы сама по себе
не вызывает вступление, чтение истории или поиск. Для Telegram администратор проверяет согласие и группу:
`/listen` → «Заявки на чаты» (или `/requests` в личном чате). В карточке есть проверка и
подтверждение подключения. `/source_approve ID КОД_ГРУППЫ` сразу одобряет заявку для указанной
группы. `all` допускается только у заявки, изначально поданной для всех пользователей cAtIx:
согласие на групповой доступ нельзя расширить этой командой. Для смены такой аудитории нужна
новая заявка с новым согласием и новой ссылкой (повтор ссылки возвращает прежнюю заявку).
`/source_reject ID причина` отклоняет заявку с видимой пользователю причиной. Повторное
подтверждение уже обработанной заявки не запускает ещё одно подключение.

На аккаунт допускается пять новых заявок за скользящие сутки. Повтор той же активной ссылки
возвращает существующую заявку и не расходует лимит. Для уже отклонённой или завершившейся
ошибкой ссылки API возвращает `409`: нужна новая ссылка либо ручная проверка администратором.
При исчерпании лимита возвращается `429`. При неопределённом результате вступления userbot
проверяет членство без повторной отправки приглашения; ожидание не всегда означает запрос
на одобрение администратором Telegram. Явный запрет на вступление или лимит членства
отображаются как ошибка, требующая вмешательства администратора.

Вступает аккаунт userbot через существующую сессию Telethon, не Bot API бот. Если Telegram
требует одобрения входа, статус остаётся «Ожидаем вступления». «Подключён» означает, что
источник включён; загрузка доступной аккаунту истории может ещё идти. История, скрытая для
новых участников самим Telegram, недоступна. Уже существующие источники не переназначаются
другой группе автоматически по новой заявке.

Для MAX одобренные заявки обрабатывает запущенный `catix-maxuserbot listen`:
разрешает ссылку, сохраняет native identity и durable join intent, затем вступает
через пользовательскую сессию. Аудитория и полная история включаются атомарно только
после свежего подтверждения доступа через CHAT_INFO и history probe. При таймауте
или обрыве ответ на join не угадывается: worker проверяет доступ, не повторяя вступление
вслепую. Уже настроенные выключенные или иначе ограниченные источники не переназначаются
автоматически; legacy-привязка остаётся ручной. Личные диалоги не подключаются.

На website backend проверяет группы через `GET /schedule-assistant/v0/me/student-groups`
с обычным пользовательским Bearer-токеном. Привязанный Telegram, `INNOHASSLE_GROUPS` и
`INNOHASSLE_SERVICE_TOKEN` для сайта не нужны. Проверка свежая на каждый запрос к агенту
(включая продолжение после подтверждения); учитываются все возвращённые группы.
При отсутствии токена, пустом списке, ошибке или некорректном ответе доступны только общие
незащищённые источники. Ручной выбор группы не даёт сайту доступа, в том числе к старым
групповым источникам. Защищённый источник с группой `all` не становится публичным.

`GET /sources/requests` возвращает `verified_groups: string[]` вместо `verified_group`.
В режиме своей группы форма подставляет единственную подтверждённую группу либо предлагает
выбрать одну из нескольких. POST заново проверяет принадлежность по пользовательскому токену;
неподтверждённая группа даёт `403`, ручной выбор группы не учитывается. В режиме «Для всех»
отправляется `group_code: "all"`; подтверждённая группа для такой заявки не требуется.
Форма показывает причину неактивной кнопки: ссылка, выбор группы, согласие или длина комментария.
Оба режима требуют модерации. При автоматической активации Telegram общей заявки устанавливается
`requires_verified_group=false`, групповой — `true`, атомарно с подключением listener;
для MAX эти заявки не активируют источник — используется отдельный Telegram-каталог MAX.
Существующие чаты не меняются, в том числе защищённые с `group_code='all'`.
Перед обновлением примените схему: миграция снимает старый запрет `all` только у таблицы заявок.

Для проверки групп по привязанному Telegram по-прежнему нужны
`INNOHASSLE_GROUPS=true` и сервисный токен со scope `users`.
Ручной выбор группы на сайте не открывает новые защищённые источники.
Боты не предоставляют пользовательский поиск по источникам.

Перед развёртыванием примените схему новым кодом (`catix-db init`, в Compose — сервис
`migrate`), затем обновите `api`, `tgbot`, `userbot`, `worker`, `maxuserbot`, если он запущен,
и website. Все читатели доступа должны использовать новую проверку; не смешивайте старые
процессы с новым API. Приглашения приватны: не публикуйте содержимое `source_requests`,
не включайте логирование HTTP-тел запросов. Отдельный сервис очереди или новая Telegram-сессия
не нужны; Telegram-заявки обслуживает `catix-tguserbot listen`, MAX подключается только вручную через каталог Telegram.

### Фоновое распознавание изображений в чатах

Перед обновлением `tgbot`, `maxuserbot` и `userbot` примените схему новым кодом (`catix-db init`,
в Compose — сервис `migrate`). OCR работает внутри этих клиентов, но не в обработчике сообщения:
постоянная `image_queue` в Postgres обслуживается по одной задаче для всех клиентов вместе.
Используется текущая `LLM_ROUTE` / `LLM_MODEL` с поддержкой изображений; отдельная Chandra не нужна.
При `LLM_PRIORITY=true` включите priority scheduling на vLLM: запросы OCR имеют приоритет 0,
а интерактивные вопросы — отрицательный. Без поддержки приоритетов оставьте настройку выключенной;
ограничение параллельности очереди продолжит работать.

Состояние очереди (SQL в административном подключении к этой базе):
```sql
SELECT status, count(*) FROM image_queue GROUP BY status;
```
После трёх неудачных попыток задача остаётся `failed`, подпись не теряется. После устранения
причины администратор может явно повторно поставить неудачные задачи:
```sql
UPDATE image_queue SET status = 'pending', attempts = 0, available_at = now(),
                       token = NULL, lease_until = NULL
WHERE status = 'failed';
```
Убитый процесс освобождает глобальную аренду не позднее чем через 300 секунд; при редактировании
сообщения старая работа не применяется. Старые сообщения автоматически заново не скачиваются.
Для MAX перед download сообщение перечитывается по native ID, URL берётся по стабильному
photo ID. Скачиваются только разрешённые HTTPS CDN без account auth и редиректов;
неизвестный CDN или недоступное изображение дают ошибку очереди, не пустое OCR.

**Если userbot пишет `Attempt 1 at connecting failed: TimeoutError`**, сеть сервера не пускает к дата-центрам Telegram (MTProto). Бота это не касается: он ходит по HTTPS на `api.telegram.org`. Проверка с сервера:
```bash
timeout 5 bash -c "</dev/tcp/149.154.167.51/443" && echo ok || echo blocked
```
Тогда userbot ходит через прокси с машины, откуда Telegram открыт, `TG_PROXY` в `.env`:
```
TG_PROXY=http://user:password@host:3128          # HTTP-прокси (CONNECT); «HTTP/HTTPS-прокси» провайдеров — это он
TG_PROXY=socks5://user:password@host:1080        # или socks4://
```
TG_PROXY=mtproxy://SECRET@host:443               # MTProxy: hex-секрет, обычный или dd...; fake-TLS (ee...) Telethon не умеет
Прокси, к которому подключаются по TLS (`https://` в адресе самого прокси), Telethon не умеет: такой адрес бот отвергает при старте. Обычный HTTP-прокси с CONNECT подходит — трафик Telegram внутри него и так зашифрован. Прокси должен разрешать CONNECT на порт 443 (дата-центры Telegram слушают 443). Проверить прокси с сервера:
```bash
curl -sS -o /dev/null -w "%{http_code}\n" -x http://user:password@host:3128 https://api.telegram.org   # 302 или 200 — прокси работает
```
Прокси нужен и для `login`:
```bash
docker compose -f docker-compose.prod.yml run --rm userbot catix-tguserbot login
docker compose -f docker-compose.prod.yml up -d userbot
```
Затем в `docker compose -f docker-compose.prod.yml logs userbot` не должно быть `Attempt 1 at connecting failed`.

## 4a. Веб-поиск (DeepSeek Search & Fetch)
Помощник по документам ищет в интернете то, чего нет в базе знаний, через [DeepSeek Search & Fetch](https://api-docs.deepseek.com/guides/search/). В `.env` нужно вписать ключ DeepSeek (не токен чата на сайте):
```
DEEPSEEK_API_KEY=
DEEPSEEK_PROXY=             # необязательно; HTTP-прокси вида http://user:password@host:3128
```
Пустой или отсутствующий `DEEPSEEK_API_KEY` отключает веб-инструменты и упоминание их в промпте. Ключ используется только для веб-поиска, настройки LLM он не меняет. После изменения `.env` перезапустите процессы приложения (в production: `docker compose -f docker-compose.prod.yml up -d --build`). Старые `TAVILY_API_KEY` и `TAVILY_PROXY` больше не используются; их можно удалить.

`search_web` вызывает `POST https://api.deepseek.com/v1/tools/search`, `read_web_page` — `/v1/tools/fetch`. В поиск уходит только поисковый запрос помощника, в Fetch — только URL ранее найденной страницы, без сообщений и данных пользователя. Поиск идёт сначала по базе знаний, затем по официальным сайтам; весь интернет — только при `anywhere=true`. DeepSeek принимает запрос до 128 символов вместе с `site:`: официальные домены группируются через `OR` в несколько запросов (до 6), результаты объединяются по `rerank_score`, повторы URL удаляются, остаётся не более 5. Сам запрос ограничен 102 символами для официальных сайтов и 128 для всего интернета, без молчаливого обрезания. Лимит помощника — 2 вызова поиска и 1 чтение страницы на вопрос; каждый HTTP-запрос провайдер тарифицирует отдельно.

Обычно `DEEPSEEK_PROXY` оставляют пустым; также действуют стандартные переменные HTTP-прокси окружения. Явный прокси допускает `http://`/`https://` с хостом и портом, не SOCKS; неверный адрес останавливает старт, пароль в ошибке не показывается.

Таймаут соединения — 5 с, ожидания данных — 20 с. При сетевом сбое, отказе ключа, отсутствии баланса (402), лимите запросов (429) или ошибке сервиса (5xx) помощник отвечает без интернета; следующие 2 минуты процесс не делает новых запросов. Результаты за последние 6 часов по-прежнему доступны из общего Redis-кэша. Отказ Fetch для отдельной страницы (403/404) не отключает остальной поиск. Логи называют DeepSeek и код ошибки, но не ключ или тело ответа.

## 5. Календарный фид
Личный календарь пользователя `GET /users/my-calendar.ics` отдаёт HTTP API (сервис `api`, порт `127.0.0.1:8004`) рядом с поиском и `/ask/`. В запросе заголовок `Authorization: Bearer <токен InNoHassle пользователя>`: подпись проверяется по открытым ключам InNoHassle (`/accounts/v0/.well-known/jwks.json`), календарь принадлежит аккаунту InNoHassle (`uid` токена; email в токене не нужен). В календаре события, которые пользователь добавил кнопкой «➕ В мой календарь» под ответами на сайте (`POST /users/my-calendar/events/{id}`) и в Telegram-боте; календарь сайта (`/calendar`) его показывает. Бот узнаёт аккаунт пользователя по Telegram id (`INNOHASSLE_SERVICE_TOKEN` со scope `users`); без токена или для того, кого InNoHassle не знает, бот держит события под Telegram id и переносит их в аккаунт, как только тот найден. Календарей групп нет. Перед портом нужен HTTPS (Caddy: `reverse_proxy 127.0.0.1:8004` для вашего домена). Если прокси отдаёт API под префиксом (`https://host/search/v0/users/my-calendar.ics`), задайте `API_ROOT_PATH=/search/v0`: API откроется и когда прокси срезает префикс (`handle_path /search/v0/*`), и когда передаёт его дальше (`handle /search/v0/*`).

Сайт продолжает читать календарь с пользовательским токеном. Для внешних приложений в карточке AI Calendar есть отдельный экспорт: пользователь явно создаёт постоянную секретную ссылку, копирует её в подписку календарного приложения и может отозвать. Экспорт содержит только сохранённые события AI Calendar, без исходных сообщений и ссылок на них; пары, спорт и бронирования из других сервисов не объединяются с ним. Обновления появляются при следующем опросе внешним приложением, не мгновенно. Отзыв прекращает последующее чтение, но не удаляет уже скачанные копии.

Перед обновлением API примените `db/schema.sql` (`catix-db init`, в Compose — сервис `migrate`): таблица `calendar_export_keys` хранит один случайный ключ чтения на аккаунт. Существующие события не меняются. Затем обновите API и website. `GET /users/my-calendar/export-key` читает существующий ключ, `POST` выдаёт его или создаёт, `DELETE` отзывает; все три требуют Bearer-токен владельца. `GET /users/calendar-export.ics?access_key=…` доступен без сессии только с действительным ключом. Этот ключ не даёт доступа к другим API и не заменяет JWT аккаунта. Ссылка остаётся рабочей после выхода с сайта; после отзыва новую нужно заново добавить во внешнее приложение.

Публичная база URL берётся из `VITE_SEARCH_API_URL` website: она должна вести на доступный из интернета HTTPS endpoint Search API с правильным префиксом. Экспорт не использует `VITE_CALENDAR_EXPORT_HOST` сервиса Schedule. Не ставьте перед ICS браузерный вход/SSO и не кешируйте его на CDN: ответ имеет `Cache-Control: no-store`. Исключите query string этого маршрута из журналов reverse proxy/CDN/APM; не записывайте `access_key`, тело ответа выдачи ключа или полный URL. Защита журнала Uvicorn внутри приложения не очищает журналы внешнего прокси. Для Nginx используйте отдельный access-log формат с `$uri`, а не `$request`/`$request_uri`, либо отключите access-log для этого endpoint; аналогично настройте Caddy. Бэкапы БД содержат действующие ключи и должны оставаться закрытыми. При утечке отзовите ссылку.

## 6. Эксплуатация
- Обновление: `git pull && docker compose -f docker-compose.prod.yml up -d --build` (схема применяется сама; вики обновляется отдельно, раздел 2a).
- Резервная копия БД: `scripts/backup.sh /srv/backups` (хранит 14 последних), поставить в cron на ночь. Восстановление: `gunzip -c файл.sql.gz | docker compose -f docker-compose.prod.yml exec -T db psql -U ctx -d ctx`.
- Состояние: `docker compose -f docker-compose.prod.yml exec worker catix-db status`.
- Алерты: воркер каждую минуту проверяет `/health` моделей, эмбеддингов и реранкера и длину очереди эмбеддингов; о проблеме (после двух неудачных проверок подряд), напоминании каждые 6 часов и восстановлении пишет всем администраторам бота в Telegram. Отключить: `ALERTS=false`.
- Очередь вопросов: агент отвечает на `AGENT_PARALLEL_QUESTIONS` вопросов сразу (по умолчанию 4), остальные ждут по очереди, по кругу между пользователями. В личке Telegram ожидающий видит «⏳ … Перед вами: N». На 1Cat-vLLM 12 вопросов разом по 4 отвечены за 106–111 с, по одному за 136 с, среднее ожидание почти то же (`experiments/load_agent.py`). Вызовы модели несут приоритет своего вопроса (`LLM_PRIORITY`, по умолчанию включён; vLLM запущен с `--scheduling-policy priority`): раньше начатый вопрос и любой вопрос бота обслуживаются раньше фоновой работы.
- Трассировка запросов агента: Phoenix, раздел 6a.
- Все секреты только в `.env` на сервере (в git он не попадает). Перед бетой перевыпустить токены, которые использовались в разработке.

## 6a. Phoenix (трейсы агента)
Phoenix показывает каждый вопрос целиком: вызовы модели, помощников и инструментов, шаги поиска (`embed`, `hybrid` с `bm25` и `vector`, `rerank`) со временем, а также оценки 👍/👎 пользователей (они хранятся как аннотации к трейсам, поэтому без Phoenix теряются).

Диалоги с вложениями тоже записываются полностью: вопросы, ответы и извлечённый текст документов/изображений, включая последующие вопросы. Исходные байты файлов и base64 изображений в трейс не отправляются. Доступ к Phoenix даёт доступ к этому тексту; удаление чата не удаляет его трассы. Обычные логи приложения по-прежнему скрывают аргументы инструментов файлового диалога.

1. Phoenix входит в `docker compose -f docker-compose.prod.yml up -d` и запускается вместе с приложениями. Адрес `PHOENIX_ENDPOINT=http://phoenix:6006` всем приложениям передаёт сам compose (`x-env` в `docker-compose.prod.yml`): `phoenix` — имя сервиса в docker-сети. Значение из `.env` (там `http://localhost:6006` для разработки) не действует, `localhost` в контейнере — сам контейнер. Проект трейсов задаёт `PHOENIX_PROJECT` в `.env` (по умолчанию `catix`).
2. В логе `tgbot` при старте строка `phoenix tracing on (http://phoenix:6006/, project catix)`.
3. Интерфейс без входа по паролю, поэтому порт 6006 открыт только на localhost сервера. Открыть со своей машины через SSH-туннель:
   ```bash
   ssh -N -L 6006:localhost:6006 server
   ```
   и в браузере `http://localhost:6006`, проект `catix`.

Трейсы лежат в той же базе PostgreSQL (`db`), в отдельной схеме `phoenix`: Phoenix сам создаёт её и сам делает миграции при старте, поэтому `scripts/backup.sh` сохраняет их вместе с остальной базой. Трейсы старше 30 дней Phoenix удаляет сам; срок задаёт `PHOENIX_RETENTION_DAYS` в `.env`. Удалить все трейсы: `docker compose -f docker-compose.prod.yml rm -sf phoenix`, затем `docker compose -f docker-compose.prod.yml exec db psql -U ctx -d ctx -c 'DROP SCHEMA phoenix CASCADE'` и `docker compose -f docker-compose.prod.yml up -d phoenix`. Выключить трейсы: убрать `PHOENIX_ENDPOINT` из `x-env` в `docker-compose.prod.yml` и перезапустить приложения.
