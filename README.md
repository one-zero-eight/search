# cAtIx

Студенческий ассистент Университета Иннополис на сайте: отвечает на вопросы про клубы, аудитории, события, расписание, а также про экзамены, дедлайны и советы из учебных чатов и ведёт личный календарь. Telegram-бот и пользовательские аккаунты Telegram/MAX собирают сообщения настроенных источников; Telegram также доставляет существующие уведомления об изменениях расписания. Диалог с агентом доступен только на сайте; CLI остаётся для диагностики.

## Возможности

- **Ответы на вопросы на сайте** (агент на LangGraph с локальной LLM через llama.cpp): поиск по чатам, клубы, события университета, карта аудиторий, расписание групп, SQL по базе сообщений.
- **Поиск по чатам**: гибридный (BM25 по словам + векторы bge-m3), слияние результатов, переранжирование `bge-reranker-v2-m3` и отсечка слабых совпадений.
- **Поиск Telegram для больших чатов**: чат можно поставить в режим «🔎 только поиск» (`/listen`): сообщения не сохраняются и не индексируются, а при вопросе агент вызывает отдельный инструмент `search_userbot_chats`: userbot ищет в нём встроенным поиском Telegram (запрос идёт через Redis), результаты ранжирует реранкер и они цитируются как обычные источники.
- **Учебные группы**: каждый чат относится к группе (`B26-CSE-01` или `all`), пользователь ищет по чатам группы `all` и своей группы (для группы `all` только по чатам `all`); свою группу пользователь настраивает на сайте, а ограничение считает код, не модель.
- **Изменения расписания**: воркер находит в сообщениях переносы, смену аудиторий и отмены и присылает их в Telegram пользователям группы чата (из общих чатов — всем); каждый сам решает, добавить ли изменение в свой календарь. Для получения существующих уведомлений нужно открыть личку Telegram-бота и нажать `/start`, а группу настроить на сайте. Кто заблокировал бота, не получает уведомления, пока не запустит его снова (таблица `bot_users`).
- **Экспорт AI Calendar**: в настройках календаря сайта можно создать секретную ссылку подписки для внешнего календарного приложения и отозвать её. Экспортируются только сохранённые события AI Calendar, без исходных сообщений и ссылок на них. Новые события, изменения и удаления доступны при следующем опросе приложения; это не двусторонняя синхронизация. Ссылка разрешает чтение любому её обладателю, а отзыв не удаляет уже скачанные копии. Требования к миграции, HTTPS и журналам — в разделе «Календарный фид» `DEPLOY.md`.
- **Календарь пользователя**: под ответом с датой события на сайте (`/ask/`) появляется кнопка «➕ В мой календарь», событие попадает в личный календарь его аккаунта InNoHassle: `GET /users/my-calendar.ics` HTTP API (заголовок `Authorization: Bearer <токен InNoHassle пользователя>`), его показывает календарь сайта. Календарные кнопки в существующих Telegram-уведомлениях сохраняются.
- **Действия с AI-календарём на сайте**: по просьбе пользователя агент добавляет, изменяет и удаляет события после подтверждения (`add_to_ai_calendar`, `update_ai_calendar`, `remove_from_ai_calendar`). Повторное добавление события с тем же названием и временем не создаёт дубликат; чужой календарь недоступен. Кнопка под ответом остаётся. Это события календаря, не автоматические уведомления; повторяющиеся события не поддерживаются. Устаревший Moodle-календарь в личное расписание больше не запрашивается.
- **Единый MCP InNoHassle**: `search_api_tools` ищет по общему каталогу FastMCP/BM25 и возвращает схемы аргументов; один `call_api_tool` выполняет чтения и изменения. cAtIx запрашивает подтверждение по явному списку имён изменяющих инструментов, независимо от роли агента. Реализация и проверка аргументов находятся на MCP-сервере; OpenAPI при запуске и вызове не загружается. Печать, сканирование и административные методы не разрешены.
- **Оценки ответов на сайте**: 👍/👎 через `POST /ask/{id}/feedback` пишутся в Phoenix как аннотация к трассе этого ответа; после оценки можно написать, что понравилось или нет, — это пояснение (`explanation`) той же аннотации.
- **Проверяемые источники ответов**: `/ask/`, финальное SSE-событие `done` и история чата возвращают текст `answer` с номерами `[1]` и отдельный массив `sources` в порядке цитирования. Каждый источник содержит номер, название, тип и доступный URL, пункты/разделы и происхождение; архивные документы сохраняют точные страницу, ревизию и имя файла. API не добавляет Markdown-список источников в `answer`; диагностический CLI формирует его из тех же данных. У старых сохранённых ответов без `sources` массив пустой, прежний текст не преобразуется. Формат результатов обычного `/search/search` не меняется.
  Календарные предложения получают ссылки и номера из того же массива `sources`, а не из разбора Markdown. Цитируемый самостоятельный дедлайн сохраняется и в смешанном ответе с расписанием; события сервисных календарей по-прежнему исключаются из повторных предложений.
- **Кнопки бронирования**: `signup_offers` создаются как после личного подбора, так и из успешных парных результатов `rooms_get_free_rooms` и `music_get_available_windows`. Варианты берутся только из проверенных свободных комнат/окон, не из текста модели. `personal_schedule_checked` отличает личный подбор от проверки только сервиса; во втором случае UI сообщает, что календарь будет проверен перед записью. Комната требует введённого пользователем названия, музыкальная комната — выбранных начала и длительности. Нажатие использует прежний model-free endpoint, свежие проверки календаря/сервиса, точное чтение результата и сохранённый `unknown` без автоповтора.
- **Управление из Telegram-бота** (админам): какие чаты слушать, какие топики форума сохранять, какая учебная группа у чата, добавление администраторов. Авторизованные администраторы вводят команды вручную; административных команд нет в меню даже у админов, `/id` доступна только им.
- **Эксплуатация**: алерты админам в Telegram, трассировка в Phoenix, образ и compose для сервера.

## Как это устроено

```
Telegram-чаты ──userbot (аккаунт, читает чаты, историю)──┐
Telegram-чаты ──Bot API бот (участник чата, с момента добавления)──┤
MAX-чаты ──userbot (аккаунт, вся доступная история)───────┤
                          фильтр шума ─► Postgres (сообщения, BM25-индекс, векторы)
                                                        │  └► embedding_queue ─► эмбеддеры ─► векторы
                                                        ▼
                                      Redis-поток ─► worker ─► изменения расписания ─► Telegram пользователям группы
Вопрос на сайте ─► guardrail ─► основной агент ─┬─► MCP: search_api_tools → call_api_tool
                                                            │   (публичные чтения; личные данные и действия с токеном пользователя,
                                                            │    изменения только после подтверждения)
                                                            ├─► локальные инструменты AI-календаря
                                                            │   (чтение; изменения на сайте после подтверждения)
                                                            ├─► ask_chats   (search_chats, search_userbot_chats, read_chats; общий MCP)
                                                            └─► ask_docs    (search_wiki, read_wiki; общий MCP;
                                                                             с DEEPSEEK_API_KEY search_web, read_web_page)
                                                                ─► ответ с источниками
```

### Граница доступа к API

Если связь с БД пропала во время календарного действия или его проверки, тул возвращает `done: null`, `outcome: "unknown"`: запись могла сохраниться. Агент сначала проверяет календарь, а не повторяет изменение автоматически. Подтверждение показывает дату с годом; поддельный аргумент `runtime` от модели не меняет аккаунт и не отключает подтверждение.

`src/catix/innohassle/mcp_tools.py` собирает явные типизированные функции со стандартным декоратором FastMCP `@tool`; реализация разбита по сервисам. `mcp_server.py` регистрирует их при запуске HTTP-сервера. Аргументы, описание, реализация и требования к пользовательским credentials определены рядом с функцией; отдельных реестров реализаций `Action` и `Operation` нет. Общий `BM25SearchTransform` публикует `search_tools` и `call_tool`. Имена инструментов сохранены. Отдельный `describe` модели не нужен: поиск возвращает схему аргументов. Клиент cAtIx использует каталог имён для выбора credentials и подтверждений, без импорта серверных реализаций.

Поиск всегда возвращает один компактный формат: `name`, `description`, `inputSchema`, без выходных схем и внутренних метаданных. Ограничения аргументов сохраняются. `services` в ответе cAtIx содержит полный список имён `tool_names` по namespace, даже если совпадений нет: отсутствие в top-5 не означает отсутствия инструмента. По точному имени можно получить его аргументы тем же поиском. Отдельного полного режима нет.

OpenAPI при запуске и вызове не загружается. Схемы получаются из Python-типов; сервер проверяет исходные аргументы до преобразования типов и применяет валидаторы конкретного инструмента до исполнения. `actions.py` содержит только модели разрешённых полей ответа и ограниченный HTTP GET-помощник; пути и параметры задаются конкретными функциями, не моделью. Необязательный `null` опускается в query, остальные разрешённые значения не подменяются. Ответы этих чтений не кэшируются. `service_status` показывает `registered`, число и все имена инструментов по namespace: это состояние каталога, а не проверка доступности внешнего API. Ошибка API не означает пустой результат.

| Namespace | Компонент | Разрешённые чтения |
|---|---|---|
| `maps` | `/maps/v0` | список карт, поиск мест и аудиторий |
| `clubs` | `/clubs/v0` | названия, краткие описания и активность клубов |
| `music` | `/music-room/v0` | занятые интервалы за день, без имён пользователей |
| `events` | `/events/v1` | опубликованные мероприятия, время, длительность и место |
| `printers` | `/printers/v0` | состояние, бумага и тонер; требуется пользовательский токен |

Модель не задаёт URL, заголовки или токен: исполнитель использует настроенный gateway и проверенный доступ вошедшего пользователя. Публичные методы не получают токен даже от вошедшего пользователя. Перенаправления запрещены; новые endpoints и параметры в Swagger сами по себе не расширяют разрешения. Низкоуровневые GET-чтения из таблицы принимают только объявленные аргументы, без произвольного тела запроса, заголовков, cookies или загрузки файлов. Их выдача ограничена 40 записями с `total` и `truncated`; внутренние IPP-адреса принтеров исключены.

Чтобы добавить чтение, нужно проверить его права и эффекты, объявить типизированную MCP-функцию с правилами доступа и покрыть её тестами — отдельный агентский тул под endpoint не нужен. Явные модели ответа отбрасывают неразрешённые поля и отклоняют неверные типы; неизвестное значение не превращается в ноль. Даже GET не считается безопасным автоматически: выпуск токенов, impersonation и административные endpoints не разрешены.

### Существующие действия через MCP

MCP-функции содержат реализацию внешних интеграций: проверки свободного времени, лимитов часов, прав бронирования и внешней регистрации на события. Они используют HTTP-клиенты сервисов, а не вызывают старые LangChain-инструменты через строковый поиск обработчиков. Правила и схемы получаются из объявлений функций без второго каталога; общие модели сохраняют доменную валидацию. Sport по-прежнему работает с `/api/v3` и отдельным Sport-токеном; запись и отмена — один вызов checkin с разными аргументами.

| Namespace | Операции |
|---|---|
| `schedule` | расписание явно выбранной учебной группы |
| `timetable` | курсы, преподаватели, пары преподавателя на конкретные даты, занятия в аудитории и свободные от занятий комнаты |
| `maps` | места, этажи и сотрудники на карте через существующую функцию поиска |
| `clubs` | поиск и фильтрация клубов до ограничения выдачи |
| `account` | внешние личные календари и брони, отмена своей брони |
| `rooms` | свободные аудитории и бронирование |
| `music` | занятые интервалы и правила доступа, бронирование; пустое расписание само по себе не доказывает доступность |
| `events` | мероприятия, запись и отмена участия; создание и изменение черновиков организатора после подтверждения |
| `sport` | часы, тренировки, виды спорта, запись и отмена |
| `when2meet` | свои опросы встреч, участники и общие слоты; создание опроса и изменение своей доступности после подтверждения |

When2Meet использует пользовательский InNoHassle-токен и четыре инструмента: `when2meet_get_my_meetings`, `when2meet_get_meeting`, `when2meet_create_meeting`, `when2meet_set_my_availability`. Изменение доступности заменяет весь набор отмеченных пользователем слотов; пустой список очищает его. Перед записью MCP заново читает опрос и проверяет архивность и выбранные слоты; успех подтверждается повторным чтением. Проверка и запись не атомарны. Общие слоты относятся только к ответившим участникам, не ко всем приглашённым. Пустой календарь не даёт агенту права публиковать доступность. Удаление, редактирование встречи и бронирование комнаты через When2Meet не включены.

`timetable_get_instructor_schedule(instructor, date_from, date_to)` разворачивает публичный `/schedule-assistant/v0/timetable` на конкретные даты: занятия, аудитории, группы, начало и конец пар и время окончания последней пары каждого дня. Обе даты обязательны и включены в интервал (до 31 дня); неизвестный преподаватель, неоднозначное имя и даты за пределами опубликованного семестра не выдаются за пустое расписание. Учитываются назначения на конкретные занятия, а не просто список сотрудников курса. Промежутки между парами не означают свободное время преподавателя: источник не показывает личные встречи. Вход и административные методы не используются.

`events_create_draft` и `events_update_draft` сохраняют название и описание на русском или английском, время с часовым поясом, место, продолжительность в часах, внешнюю ссылку регистрации и необязательный клуб-организатор. Текст описания преобразуется в JSON TipTap, который ожидает сайт Events. Перед созданием проверяются роли `club-leader`/`event-manager` через `/events/v1/users/me`; перед изменением — свежий `can_edit` конкретного черновика. Добавлять можно только собственный клуб. Обычный вход студента не гарантирует этих прав; сервисный токен не используется. Живая проверка с обычным студенческим токеном не проведена: нужен отдельно предоставленный тестовый пользовательский доступ. Запрет для обычного пользователя подтверждён опубликованными исходниками upstream и синтетическими HTTP/MCP-тестами, не production-запросом.

Оба действия требуют подтверждения cAtIx и проверяют сохранённые поля повторным GET. При изменении пропущенные/`null` поля остаются прежними, пустое описание очищается; другая языковая версия не перезаписывается. `registration_url` заменяет способ записи на внешнюю регистрацию, `club_id` добавляет организатора, не удаляя остальных. Удаление времени/места/длительности и управление произвольными ссылками, приглашениями, изображением в этот первый набор не входят. Сохранение состоит из нескольких запросов и неатомарно; нет защиты от параллельного редактирования upstream. После частичного сбоя результат `unknown` сохраняет известный `draft_id`, автоматического повтора или отката нет. Отдельного чтения черновиков пока нет — неоднозначный результат проверяется на сайте Events. Отправка через `/submissions/{id}`, публикация и модерация не вызываются; будущая отправка должна быть отдельным подтверждаемым действием.

AI Calendar не входит в MCP. Для личного расписания агент вызывает один host-инструмент `get_my_schedule`: он объединяет выбранные учебные календари, спорт, записи на мероприятия и брони из MCP с локальным AI Calendar. Общий список отсортирован по времени, содержит `starts_at`/`ends_at` с часовым поясом, источник и исходные ID. Все источники читаются за один период; по умолчанию — семь дней от даты вопроса. `sources`, `complete`, `not_read` и `truncated` отличают пустое расписание от неполного чтения. Без credentials возвращается доступная часть и, при известной группе, явно отмеченное публичное расписание; оно не определяет выбранный английский. Сбой личного источника у вошедшего пользователя не подменяется групповым расписанием.

Когда сайт передал отдельный Sport-токен, сборка личного расписания читает `/users/me/schedule` Sport напрямую за запрошенные даты: от местной полуночи первого дня до исключающей полуночи после последнего. В календарь попадают только подтверждённые `checked_in` тренировки; многодневные/all-day интервалы сохраняются. Это убирает путь Schedule → Accounts → Sport и фиксированное окно ICS ±7 дней, но не гарантирует доступность внешнего сервиса. Без отдельного токена остаётся прежняя персональная ICS-лента. Ошибка прямого Sport-чтения не запускает повтор или ICS-fallback: остальные компоненты сохраняются, а личная доступность остаётся неизвестной.

Обычный запрос свободной аудитории на точное время использует `rooms_get_free_rooms`: занятость и права Room Booking без личного календаря. `get_my_available_rooms` предназначен только для явно запрошенной совместимости с личным расписанием. Свободная по сервису комната и свободное время пользователя — разные результаты; сбой Sport не должен скрывать сервисную доступность. Поиск не создаёт бронь и не заменяет существующие проверки/подтверждение записи.

Для музкомнаты обычный запрос доступности или общих окон использует `music_get_available_windows`: занятость, доступ и квоты сервиса, без личного календаря. Только явная просьба «когда я свободен» / «без пересечений с моим расписанием» использует `get_my_available_music_windows` и личные события. В обоих маршрутах точный запрос передаёт `time_from` и `time_to`; одной длительности недостаточно. Сервис возвращает только `requested_interval` или причину отказа: пересекающаяся бронь (`room_occupied`), часы работы, лимит, доступ либо неизвестность. В личном маршруте календарь читается лишь после успешной проверки сервиса, а модель получает только реально пересекающиеся события. Без точного времени сохраняется подбор окон за день. Бронь не доказывает авторство другого человека. Кнопка записи сохраняет свежие проверки перед изменением; просмотр общих окон не гарантирует совместимости с личным расписанием.
Название сервиса определяется до общих правил комнат: `music room` / `музкомната` не означает аудиторию Room Booking. Уточнение пользователя отменяет прежний выбор сервиса и требует свежей проверки музыкальной комнаты на тот же точный интервал; старые результаты аудиторий не служат подтверждением.

Для явно отдельного AI Calendar остаётся `get_my_ai_calendar`. Локальные `add_to_ai_calendar`, `update_ai_calendar` и `remove_from_ai_calendar` требуют подтверждения и входа на сайт; кнопки и ICS используют прежнее хранилище `personal_calendar.py`. Проверка пересечений перед записью на Sport использует ту же сборку `get_my_schedule`, повторно читает её после подтверждения и останавливает запись при конфликте либо неполных данных. Эта программная проверка пока не распространяется на брони и изменения AI Calendar. Владелец локального календаря и Telegram ID не передаются в MCP.

Обычный запрос списка/подбора тренировок использует `sport_get_sport_trainings`: результаты Sport с `checked_in`/`can_check_in`, без фильтрации по личным занятиям, броням или AI Calendar. «Подбери мне» и «на что можно записаться» сами по себе не означают проверку личного свободного времени. Только явная просьба «без пересечений с моим расписанием» использует `get_my_available_trainings(day, sport=None)`: он объединяет Sport и личный календарь на точный день и делит варианты на `available`, `excluded` и `unverified`. Неполный календарь не считается свободным временем; `can_check_in` означает разрешение Sport, не отсутствие личных конфликтов. Оба маршрута чтения ничего не записывают. Перед фактической записью сохраняются подтверждение, свежая проверка личного календаря и сервиса; неизвестный результат не повторяется. Запрошенный день всегда ограничивает даты этим днём, а не неделей по умолчанию.

Отдельных campus- и account-помощников нет: основной агент сам читает данные аккаунта и выполняет запрошенные действия. Docs и chats остаются помощниками для поиска по документам и чатам. Все три агента используют одинаковые `search_api_tools` и `call_api_tool`, без проверки роли для доступа к MCP. Общие инструкции API включают проверку доступности перед бронированием, отдельный Sport-вход, запрет угадывать параметры и повторять действие при неизвестном результате. Везде, где доступен вызов, установлен HumanInTheLoop с одним списком имён, требующих согласия. Неизвестные имена и вложенные вызовы интерфейсных инструментов отклоняются. Личные данные и действия по-прежнему требуют пользовательских credentials; публичные методы доступны без входа. Локальные изменения AI-календаря доступны только оркестратору с токеном и идентификатором владельца и подтверждаются отдельно. Описание возможностей зависит от credentials и доступных локальных инструментов, а не от наличия роли account. Правила об ограничениях расписания, сведениях из чатов и различии свободной от занятий аудитории и доступной для бронирования сохранены.

Блок `MCP_RULES` добавляется только в промпт супервизора. Промпты docs и chats содержат общие правила фактов и свой поисковый блок (docs также получает WEB при доступном веб-поиске); доступные им API-инструменты и программное согласование не меняются. Отдельного brief-режима, лимита около 40 слов и запрета развёрнутых оговорок больше нет: действуют обычные правила краткости и раскрытия неполноты. Официальность конкретного сообщения определяется только его `official` из административных метаданных. Самоописание текста не подтверждает статус, а официальный чат сам по себе не доказывает авторство администрации.

Поведенческие `ROLE_REMINDER` и `ALONE_REMINDER` больше не дописываются к вопросу и не создают отдельный `HumanMessage`. Правила выбора задачи, уточнений, действий, языка и ответа о возможностях находятся в системном промпте. `QuestionNoteMiddleware` сохраняет только вычисленные даты и, для помощников, расшифровки сокращений; сохранённую историю он не изменяет. Для `answer_alone` программный запрет инструментов в `RunGuardMiddleware` сохранён.

Thinking обязателен на каждом вызове супервизора, включая решения после инструментов, финальный ответ, small talk и запуск без guardrail. Используются `temperature=0.85`, `top_p=0.95`, `top_k=20`, `min_p=0.0`, `presence_penalty=1.1`, `repetition_penalty=1.0`. Опция `AGENT_PLAN_THINKING` удалена; `answer_alone` не отключает thinking. Помощники сохраняют прежний режим. `LLM_PLAN_MAX_TOKENS` задаёт бюджет каждого вызова супервизора, а не только первого.

Основной маршрут chats выбирается взаимоисключающе: списки, подсчёты, последние сообщения и сообщения автора начинаются с `read_chats`; отдельный тематический факт или обсуждение — с одновременных `search_chats` и `search_userbot_chats`. Например, «все дедлайны на следующей неделе» — список с `event_from/event_to`, а не тематический поиск. Дополнительное чтение или поиск допустимы только для конкретного непокрытого пункта после основного запроса. Поисковая выдача не доказывает полноту и не заменяет подсчёт; `total` относится к сообщениям по фильтрам, не к уникальным событиям.

Временная ось chats выбирается по смыслу периода, независимо от списка, подсчёта или тематического ответа: «что состоится / все дедлайны на следующей неделе» — `event_from/event_to`, включая заранее опубликованные объявления; «что написали / сколько сообщений о дедлайнах написали за неделю» — `date_from/date_to`. Обе оси применяются только при явном ограничении обеих дат пользователем. Для неоднозначного периода требуется уточнение. Даты в `search_userbot_chats` ограничивают публикацию, не дату события; при запросе только о событиях эти фильтры не передаются, даты событий проверяются по результатам.

Исключение из уточнения неизвестной длительности действует только при создании нового личного timed-события AI Calendar с известными датой и началом: `proposed_duration_minutes=90` — явное предложение на native approval, не факт об окончании. Если пользователь хочет оставить конец неизвестным, предложение не передаётся. Для бронирований, записи на услуги, проверки доступности, all-day и изменения существующего события это исключение не применяется; неизвестное окончание старого события не превращается в 90 минут и не доказывает свободное время. При изменении сохраняется прежний известный или неизвестный конец, если пользователь не просил менять его; необходимый для запрошенного изменения неизвестный конец уточняется.

Аудитория объявления определяется по содержанию с учётом известных групп пользователя, а не по одному `group` источника. `all` означает общий чат, не применимость каждого сообщения ко всем; явное «для B26-CSE-01» сохраняется и в общем чате. Общевузовское объявление в групповом чате не становится групповым. Если аудитория не установлена, агент обозначает источник, не приписывая факту универсальную или личную применимость; существенную неопределённость уточняет. Правила доступа к чатам и рассылки уведомлений этим изменением не затрагиваются.

Для `schedule_get_schedule` клиент подставляет известную учебную группу из доверенного контекста или принимает группу, явно названную в вопросе. Если группа неизвестна, спрашивает её, а не берёт пример из описания инструмента. В MCP передаётся только выбранная публичная группа, не весь контекст или текст вопроса. Чтение AI-календаря на сайте остаётся локальным инструментом основного агента с прежним определением владельца; Telegram ID и владелец календаря не становятся аргументами анонимного MCP. Кнопки календаря на сайте и в существующих Telegram-уведомлениях сохранены.

Перед подтверждением внешнего изменения клиент проверяет аргументы по `inputSchema` из настоящего результата поиска; если схемы ещё нет, получает её анонимным поиском точного имени. Отдельного ручного каталога обязательных полей нет. Например, отсутствие `title` возвращается модели для уточнения без подтверждения и записи. Бизнес-правила остаются на MCP-сервере.

После проверки схемы backend cAtIx локально формирует описание на русском или английском: `agent/api_descriptions.py` содержит явные шаблоны операций, `agent/api_context.py` дополняет их названием, датой, временем и местом тренировки, мероприятия или отменяемой брони. Детали берутся из успешных результатов соответствующего инструмента в текущем запросе с точным совпадением ID (для брони — также сервиса), а не из текста модели. Если данных нет или они неполны, выполняется обычное чтение через `sport_get_training`, `events_get_event` либо `account_get_booking`. Последний возвращает только собственную бронь; для музыкальной комнаты выбирает точный ID из личного списка. Если существенные детали недоступны, подтверждение не предлагается и изменение не выполняется. Дополнительной модели и отдельного `preview_tool` нет.

Неуказанные значения по умолчанию берутся из `inputSchema` только для отображения; исходные аргументы исполнения не меняются. Ошибка получения схемы, проверки аргументов или формирования текста останавливает подготовку. Описание связано с точным вызовом и сохраняется в checkpoint до HumanInTheLoop, поэтому продолжение после ответа пользователя не повторяет поиск схемы, чтение деталей и форматирование. Ожидающая карточка сохраняет это описание при повторном открытии чата, даже если модель не написала пояснение. Уточнение недостающих данных не считается согласием на действие; MCP elicitation здесь не используется. Карточка не резервирует место и не гарантирует успешное выполнение.

Описание ожидающего действия показывается только в карточке подтверждения (`approval.actions`), без копирования в `answer`. Отдельное пояснение ассистента сохраняется; если его нет, ответ лишь предлагает подтвердить или отклонить действие в карточке.

После согласия выполняется обычный MCP-вызов с пользовательскими credentials; сервер проверяет аргументы, права и бизнес-ограничения. Подтверждение не является dry-run и не гарантирует выполнимость: например, межполевые ограничения времени проверяются при исполнении, а не при формировании текста. Серверных билетов и общего хранилища подтверждений нет. При сетевом сбое, таймауте записи или ответе сервера 5xx результат считается неизвестным: `done: null`, `outcome: "unknown"`, без автоматического повтора; сначала нужно прочитать состояние.

Локальные календарные изменения проходят собственное подтверждение оркестратора и проверку владельца, без MCP. Прежние проверки времени, идемпотентности, коллизий и неизвестного результата записи сохраняются.

### Запуск MCP

MCP всегда работает отдельным HTTP-процессом. Адрес клиента по умолчанию — `INNOHASSLE_MCP_URL=http://127.0.0.1:8010/mcp`. Запуск вручную: `uv run catix-mcp` (по умолчанию слушает только `127.0.0.1:8010`); проверка готовности — `GET http://127.0.0.1:8010/health`. Каталог собирается один раз при старте сервера, а не на каждый поиск или вызов. После изменения состава инструментов или схем сервер нужно перезапустить. Для каждого запроса клиент создаёт отдельную сессию с его credentials. Если сервер недоступен, клиент возвращает ошибку и не запускает in-process сервер или обходной прямой HTTP-вызов.

`scripts/catix.sh up` запускает MCP до приложений и ждёт `/health`; `down` останавливает его после клиентов, `status` проверяет HTTP, `logs mcp` показывает журнал. В production Compose есть отдельный сервис `mcp`: приложения обращаются к `http://mcp:8010/mcp` внутри Docker-сети и ждут готовности сервиса. Его порт не публикуется на хосте. HTTP разрешён для loopback и этого внутреннего Compose endpoint; для других адресов требуется HTTPS. URL не должен содержать credentials, query или fragment.

Для локальной проверки Events и Clubs можно независимо задать `INNOHASSLE_EVENTS_API` и `INNOHASSLE_CLUBS_API`, оставив `INNOHASSLE_API=https://api.innohassle.ru` для Accounts/JWKS и остальных сервисов. Это **полные корни API**, заменяющие `/events/v1` и `/clubs/v0`, а не адреса общего gateway. Например, `INNOHASSLE_EVENTS_API=http://127.0.0.1:9101` направит `/events/v1/drafts/` на `http://127.0.0.1:9101/drafts/`; если сервер обслуживает `/api/v1/drafts/`, укажи `http://127.0.0.1:9101/api/v1`. Аналогично `INNOHASSLE_CLUBS_API=http://127.0.0.1:9102` направит список клубов на `/clubs/`. Порты здесь — примеры. Конечный `/` в настройке необязателен; пустая или отсутствующая настройка оставляет сервис на общем gateway. Credentials, query и fragment в URL запрещены.

Переопределения распространяются на публичные и личные чтения, Events ICS, действия и проверочное чтение после записи. Кеш публичных ответов разделён по полному адресу API. При ошибке локального сервиса запрос не повторяется в production, redirects не выполняются. Это не глобальный sandbox: остальные сервисы по-прежнему работают через общий gateway. Указывай только доверенные серверы: защищённые методы Events получают пользовательский InNoHassle-токен; сервер должен принимать его и иметь нужные роли/данные. Проверки прав и подтверждение cAtIx не отключаются.

После изменения настроек перезапусти `catix-mcp` и другие процессы cAtIx, использующие этот клиент; для запуска через `scripts/catix.sh` — `down`, затем `up`. В Docker адрес должен быть доступен из контейнера MCP: `127.0.0.1` обозначает сам контейнер, а не хост. Настройки website независимы: для просмотра локальных черновиков укажи там `VITE_EVENTS_API_URL` и `VITE_CLUBS_API_URL`; URL страниц в ответах cAtIx эта настройка не меняет.

Это внутренний адаптер, не публичный OAuth-сервис. Клиент cAtIx передаёт делегированный токен через `X-Innohassle-Token`, отдельный Sport-токен через `X-Sport-Token`, не через аргументы инструмента. Сервер проверяет подпись и `uid` InNoHassle отдельно для каждого запроса. `Authorization`, `Cookie` и MCP `_meta` не выбирают upstream-аккаунт. Для каждого вызова создаётся отдельная клиентская сессия и контекст авторизации; общий admin-токен не используется.

MCP-сервер не проверяет подтверждение пользователя: другой клиент с действительными credentials может вызвать изменение напрямую. Подтверждение — ответственность клиента, а проверки аргументов, аккаунта и бизнес-ограничений остаются на сервере. Redis для подтверждений не нужен; его использование общим кэшем и остальными компонентами cAtIx не меняется. Публикация MCP наружу требует отдельной настройки TLS, доступа и ограничения нагрузки; текущий deployment остаётся приватным.

`uv run catix-maxuserbot chats` читает каталог групп/каналов из сохранённой сессии,
не запускает повторный вход и не выводит личные диалоги. `MAX_SESSION` по умолчанию
`data/max/account.db`; файл, SQLite sidecars и каталог должны оставаться приватными
(0600/0700). Сессия даёт доступ к пользовательскому аккаунту: не включать в backups,
логи и артефакты. Одновременно сессию использует только одна команда (flock).
`login --replace` требует подтверждения удаления локальной сессии и не завершает
другие сеансы MAX. Клиент PyMax (`maxapi-python` 2.5.0, MIT) закреплён на git revision
`c4cb917d354a1179be625925530d72c8aaa969ff`; API неофициальный, возможны изменения
протокола и блокировка аккаунта. Проверка совместимости с живым MAX требует оператора.

MAX-каталог пользовательского аккаунта отделён от Telegram и старого Bot API: новые
чаты получают namespace `4*10**15 + raw_id`, сообщения — native int64 ID.
Допустимый raw chat ID: строго `(-10**15, 10**15)`; итоговый DB ID остаётся
строго в `(3*10**15, 5*10**15)`, вне Telegram и legacy MAX namespaces.
Живой каталог MAX содержит отрицательные 47-битные ID, поэтому прежний предел
`10**13` был недостаточен. Существующие DB IDs от расширения диапазона не меняются.
Новые источники выключены и закрыты для поиска до явного выбора аудитории. Включение
требует свежей проверки доступа и heartbeat работающего account worker.
Привязку прежнего MAX-источника подтверждает администратор: только после включения
связанный legacy-чат скрывается из всех поисковых scope, включая явный ID и SQL.
Его сообщения, OCR и прежняя аудитория остаются в БД; выключение нового источника
не возвращает архив в поиск. Непустые таблицы незавершённой Bot API state-схемы
блокируют миграцию понятной ошибкой вместо удаления данных.

`catix-maxuserbot listen` не отправляет сообщения, read receipts, typing или reactions.
Единственное исключение из пассивного режима — автоматическое вступление по заявке
с сайта после одобрения модератором cAtIx. Одобрение ставит заявку в очередь account
worker, а не доказывает доступ: администратору чата может потребоваться одобрить
вступление. Индексация и вся доступная история включаются только после свежей
проверки доступа. При таймауте вступления worker проверяет текущее членство,
не повторяя join вслепую. Права администратора MAX-аккаунту не требуются.
WebSocket admission последователен до библиотечного task fanout;
после commit inbox обработка message/fence/outbox атомарна. До собственного commit
нет upstream ACK/replay-гарантии: авария может потерять frame, exactly-once от MAX
не обещается. Native explicit удаления оставляют постоянный tombstone. Новые/правленые
сообщения перечитываются через MSG_GET с сохранённой локальной observation, а не
версией по времени создания. Redis outbox подтверждается только strict publish;
отсутствие Redis не считается успехом. Личные диалоги и тела выключенных источников
не сохраняются. При ошибках БД приём прерывается, сессия восстанавливается без QR.

Включение, повторное включение и ручной повтор загружают всю историю, доступную
аккаунту через API, без `TG_SYNC_DAYS` и возрастного cutoff. Курсор полной истории
сохраняется между перезапусками. Catchup имеет отдельный курсор/интервал разрыва;
пока gap не восстановлен, heartbeat не продвигает watermark. Завершённый архив
не означает отсутствия gap; offline правки/удаления восстановить полностью нельзя
обещать. Timestamp pagination без продвижения останавливается с `partial`, не
пропускает миллисекунду и не сообщает ложный успех. Неподтверждённый range-delete
API проверяет сохранённые native IDs через MSG_GET: удаляет только явные REMOVED,
отсутствующие IDs оставляют `deletion_reconciliation_partial`.
MAX OCR хранит только `photo:<native_id>` и перед download перечитывает сообщение:
подписанная CDN URL не сохраняется, account auth на CDN не передаётся. Source
generation проверяется под блокировкой при OCR finish; off→on не оживляет claim.

Управление: Telegram `/admin` → «Группы и источники» → «MAX» (либо `/listen` → MAX).
Каталог обновляется кнопкой через worker, без MAX-сети из Telegram handlers.
«Настроить» использует общий с Telegram выбор учебной группы (готовые коды,
постраничный список и ввод другого кода), явную аудиторию «Для всех» и режим всего
чата «Хранить»/«Выключен», затем выбор legacy-источника и review перед сохранением.
«Дополнительно» использует тот же флаг `chats.official` и подтверждаемую очистку
сообщений. Очистка MAX сохраняет аудиторию, включённость, официальность и tombstones,
но останавливает текущую загрузку архива и блокирует результаты старых fetch/OCR;
новый архив загружается только по явному повтору или повторному включению.
Топики и выбор bot/userbot в MAX не предлагаются: закреплённый клиент содержит
комментарии к постам (`postId`), но не Telegram-подобные форумные топики.
Режим поиска без хранения доступен только Telegram, MAX его не имитирует.
Старый архив скрывается только после подтверждённого включения. «Выключить» сохраняет
контент; «Повторить историю» запрашивает полный архив. Карточка отдельно показывает
полную историю и восстановление gap. Черновики привязаны к администратору, личному
чату, nonce и версиям source; отмена/команды/переход в Telegram сбрасывают черновик.

Внешние сервисы:

- **Postgres** (ParadeDB: `pg_search` для BM25 и `pgvector` для векторов) и **Redis** (поток новых сообщений и общий кэш всех процессов: InNoHassle, Sport, DeepSeek Search & Fetch, выбор `/listen`, `src/catix/common/cache.py`).
- **llama.cpp**-серверы: чат-модель (`LLM_ROUTE`), эмбеддинги `bge-m3` (`EMBEDDINGS_ROUTE`), реранкер `bge-reranker-v2-m3` (`RERANKER_ROUTE`, необязателен).
- **InNoHassle** (клубы, события, расписание групп; токен пользователя открывает его календарь), **Arize Phoenix** (трассировка, один контейнер, необязателен).

## Быстрый старт (разработка)

Нужны Python 3.13, [uv](https://docs.astral.sh/uv/), Docker и доступные llama.cpp серверы.

```bash
cp .env.example .env                 # заполнить (минимум: POSTGRES_PASSWORD, READER_PASSWORD, TG_BOT_TOKEN, маршруты моделей)
uv sync
scripts/catix.sh up                  # Postgres+Redis, схема БД, SSH-туннель к GPU, боты, воркер, userbot
scripts/catix.sh status              # что работает
scripts/catix.sh logs tgbot          # логи (tgbot, maxuserbot, worker, tguserbot)
scripts/catix.sh down                # остановить приложения
```

Один раз для userbot: `uv run catix-tguserbot login` (код из Telegram, 2FA). `uv run catix "вопрос"` остаётся диагностическим запуском агента из терминала.

MAX подключается отдельно: `uv run catix-maxuserbot login` → `chats`, затем
`scripts/catix.sh up` запустит `listen` только при наличии файла `MAX_SESSION`.
Источники включаются через Telegram-каталог либо по одобренной заявке сайта после
подтверждения доступа, не фактом входа в аккаунт. После обновления нужно перезапустить
существующий MAX worker: ранее одобренные заявки подхватятся без ручной правки БД.
Реальное вступление и доступ в живом MAX этим описанием не подтверждаются.
Порядок переключения прежней установки и ограничения проверок — в [DEPLOY.md](DEPLOY.md).

## Настройка в боте

Админы (`ADMIN_TELEGRAM_IDS` и добавленные через `/admin`) в личке с Telegram-ботом вводят команды вручную. Они скрыты из меню команд для всех, включая админов; `/id` также требует прав администратора:

| Команда            | Назначение                                                                                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/listen`          | список чатов (userbot и бота): слушать или нет, кто читает (userbot, бот или авто), топики форумов, учебная группа чата, отметка «🏛 официальный» (удобнее, чем `/official`), очистка сохранённых сообщений чата (с подтверждением) |
| `/admin`           | список администраторов, добавить или убрать (по id или пересланному сообщению)                                                                                                 |
| `/id`              | id чата и топика                                                                                                                                                               |
| `/official`        | список чатов и отметка «официальный» (`/official 4` переключает, `/official 4 on\|off` задаёт): только такие чаты агент вправе называть официальными, в списке источников они помечены «(официальный чат)» |
| `/abuse`           | нарушители за сутки, пауза и последние остановленные сообщения (`/abuse tg:123`), снять паузу и забыть нарушения (`/abuse clear tg:123`) |

Для пользователей Telegram-бота остаётся `/start`: он включает получение существующих уведомлений об изменениях расписания. Учебная группа, вопросы ассистенту и личный календарь доступны на сайте. Telegram-бот не отвечает на вопросы в личке, по упоминанию, ответом или inline. MAX userbot пассивен: личные диалоги и команды, включая `/start`, полностью игнорируются; отправок и уведомлений MAX нет.

Для Telegram бот должен быть администратором или иметь отключённый privacy mode (@BotFather → `/setprivacy`); настройка чтения выполняется в `/listen`. При каждом запуске `catix-tguserbot listen` и переподключении Telegram userbot автоматически повторно читает историю за `TG_SYNC_DAYS` (по умолчанию 365 дней), одновременно принимая новые сообщения. Повторное чтение не зависит от ID уже пришедшего live-сообщения, поэтому оно не пропускает более ранние сообщения внутри этого окна; сохранение и очередь индексации используют прежний путь синхронизации. Загружаются только доступные аккаунту чаты, назначенные userbot для хранения, и разрешённые топики; режимы «только поиск», «выключено» и чтение ботом не включают такую загрузку. Пропуски старше окна автоматически не восстанавливаются; `catix-tguserbot sync` остаётся отдельной ручной инкрементальной синхронизацией. MAX использует отдельный каталог, явную аудиторию и всю доступную аккаунту историю без возрастного ограничения; добавление аккаунта в чат само по себе не включает индексацию.

## Супервизор и помощники (subagents)

Один длинный промпт с семью инструментами плохо работал на маленькой модели: она выполняла из него мало правил (оба поиска по чатам
в одном шаге вызывались в 1 вопросе из 8, с коротким промптом одной роли и двумя инструментами в 8 из 8). Поэтому агент разделён по
паттерну subagents из LangChain (`agent/core.py`, тексты в `agent/roles.py`):

- **Супервизор** общается с пользователем. В его промпте только правила поведения: роль, закон и этика, без рекламы, язык, краткость.
  Его инструменты это помощники `ask_chats` и `ask_campus`. Он формулирует вопрос помощнику целиком (раскрывает «а в какой
  аудитории?» по истории), при необходимости вызывает обоих сразу и отвечает только по их отчётам. Приветствия и отказы он
  обрабатывает сам.
- **Помощник** это отдельный агент (`create_agent`) со своим промптом (правила про факты, источники, даты и `official` плюс свой
  блок) и своими инструментами. У него нет памяти между вызовами (`checkpointer=False`), длинные результаты поиска остаются
  внутри него. Отчёт проходит проверку кодом (выдуманные ссылки и приписывания администрации вырезаются), источники возвращаются в
  состояние супервизора, поэтому номера `[m0]` продолжаются по всему диалогу. Вызовы инструментов помощника лежат в `artifact`
  сообщения (видны в трассах и тестах).
- **guardrail** остаётся только экраном: он решает `ok`, `prompt_injection` или `abuse` и ничего не маршрутизирует.

Цена: на вопрос приходится минимум два вызова модели супервизора (вызвать помощника и ответить) плюс вызовы помощника. Зато
промпты короткие, и правила про инструменты и факты не мешают правилам поведения.

## Экран перед агентом (guardrail)

Сначала несколько узких шаблонов ловят классические джейлбрейки без обращения к модели («ignore all previous
instructions», «покажи свой системный промпт», «ты теперь DAN»; `QUICK_PATTERNS`), каждый требует глагол-приказ и цель, поэтому
обычный вопрос про «правила общежития» проходит. Остальное решает короткий вызов той же локальной модели (`agent/guardrail.py`, около 0,4 с,
ответ ограничен схемой до одной категории; в промпте экрана список известных формулировок джейлбрейков): `ok`, `prompt_injection` (смена роли и правил, просьба показать инструкции,
«в каждом ответе…», реклама), или `abuse` (оскорбления, взлом, чужие
персональные данные). Не `ok` отвечается фиксированным отказом на языке сообщения и до агента не доходит. Если экран не
смог ответить (сервер модели недоступен), сообщение идёт дальше: остаётся промпт агента. Включён всегда (без настройки),
заблокированные сообщения пишутся в лог (`blocked a message as …`): так видно ложные срабатывания. Экран смотрит только на
последнее сообщение; инъекции, спрятанные в сообщениях чатов, он не видит, от них защищают промпт агента и проверка ниже.

### Повторные нарушения и паузы

Экран считает остановленные сообщения по пользователю (`tg:<id>`, `max:<id>`; `abuse.py`). Считаются только попытки менять
правила бота и оскорбления; просьба рассказать анекдот или написать код отклоняется, но не засчитывается. Админы не считаются.
Окно подсчёта 24 часа и только после последней паузы.

| Нарушение в окне | Что получает пользователь |
| ---------------- | ------------------------- |
| 1–2              | обычный отказ |
| 3–4              | отказ и предупреждение «такие запросы нарушают правила использования, доступ может быть ограничен» |
| 5                | пауза 15 минут; каждая следующая вдвое дольше (30, 60 … максимум 24 часа); неделя без пауз сбрасывает счёт |
| во время паузы   | на любое сообщение (и обычный вопрос) короткий ответ «доступ ограничен до HH:MM», модель не вызывается |

Пороги и сроки настраиваются (`ABUSE_ENABLED`, `ABUSE_WARN_AT`, `ABUSE_PAUSE_AT`, `ABUSE_WINDOW_HOURS`, `ABUSE_PAUSE_MINUTES`,
`ABUSE_PAUSE_MAX_HOURS`, `ABUSE_FORGET_DAYS`). Админам ничего не отправляется: список и снятие паузы по команде `/abuse`
(превью остановленных сообщений хранятся 30 дней).

## Проверка ответа кодом

Маленькая модель дописывает правдоподобное: «администрация сообщает…», «уточните у старосты», «это не анонсировалось». Поэтому
перед отправкой `agent/claims.py` проверяет атрибуции по структурированным записям именно процитированных источников, включая
исходные результаты в artifact отчёта помощника. Для официальности все процитированные записи должны иметь `official: true`;
самоописание текста, чужой официальный источник, неизвестная ссылка или конфликт метаданных не подтверждают статус.
Для прочих проверяемых атрибуций требуется соответствующее упоминание в тексте каждого процитированного источника.
Это проверка атрибуции, не истинности всех фактов. Неподтверждённые предложения удаляются и записываются в лог.

Целевые проверки после аудита: регрессии `claims.check` покрывают чужой официальный источник, неизвестные/смешанные ссылки, самоописание и конфликт метаданных, а также проверку исходных результатов помощника. Модельные пробы не дали общей гарантии: с вычисленной подсказкой дат список следующей недели выбрал правильный период, но тематический запрос вызвал только `search_chats` вместо обязательной пары. Пробы supervisor с синтетическими источниками выявили обращения к помощникам вместо уточнения неполного запроса; тест Events остановился на первом `ask_docs`, до обращения к сервису и timeout. Разбор трасс также установил, что при `guardrail=False` в графе отсутствует канал `answer_alone`: переданный в этих тестах `False` теряется и planner не включается. Поэтому эти результаты не измеряют supervisor с включённым planner. Текст вызова инструмента в прямой пробе `ChatOpenAI.invoke` получен в обход штатного `RunGuardMiddleware` и сам по себе не доказывает утечку markup через рабочий граф.
По умолчанию все чаты неофициальные; отметьте официальные, например канал администрации (`Campus Information`).

## Что сохраняется и что нет

Фильтр шума (`ingest/noise.py`) не сохраняет приветствия («Привет», «Доброе утро, ребята»), тексты до трёх букв без цифр, сообщения из одних эмодзи и подписи-заглушки медиа (`[file: sticker.webp]`). `DROP_NOISE=false` отключает. Документы, ссылки и сообщения с содержанием остаются. Уже сохранённое чистят `catix-db prune-noise` и `catix-db dedupe` (с предпросмотром).

| `API_HOST`, `API_PORT`, `API_ROOT_PATH`                           | HTTP API `catix-api`: поиск, `/ask/` и личный календарь `/users/my-calendar.ics`; префикс за прокси |
| `PHOENIX_ENDPOINT`, `PHOENIX_PROJECT`                             | трассировка в Phoenix (`http://localhost:6006`; в `docker-compose.prod.yml` всегда `http://phoenix:6006`) и оценки 👍/👎 (пусто = выключена)  |
| `ALERTS`, `ALERT_QUEUE_MAX`                                       | алерты админам                                                                        |

`TG_CHATS` и `TG_TOPICS` только стартовый список: при первом запуске копируются в базу, дальше чаты выбираются в `/listen`.

## Тесты

Тесты проверяют поведение настоящего агента, поэтому им нужны работающие Postgres и модели
(`scripts/catix.sh up`). Если сервер модели не отвечает, тесты пропускаются с подсказкой, а не падают.

```bash
uv sync                                       # ставит и dev-зависимости: pytest, deepeval, deepteam
uv run pytest                                 # все тесты, кроме атак DeepTeam (около 4 минут)
uv run pytest -m redteam                      # только атаки DeepTeam (около 9 минут)
uv run pytest -m "redteam or not redteam"     # вообще всё (около 12 минут)
TEST_WITHOUT_GUARDRAIL=1 uv run pytest -m redteam   # атаки на сам агент, без экрана (иначе почти всё отсекает экран)
uv run pytest tests/test_change_detection.py  # один файл (около 30 секунд)
uv run pytest -k "english or extrapolate"     # тесты по части имени
```

**Трейсы тестов.** Каждый вопрос агенту в тестах идёт внутри корневого спана, и трейс попадает в Phoenix, в проект `catix-tests`
(не вперемешку с настоящими). У упавшего теста ссылка на трейс печатается в его отчёте (секция `Phoenix traces`) и в сводке в конце
прогона: `http://localhost:6006/projects/<проект>/traces/<trace id>`. Там видно, какого помощника вызвал супервизор, какие запросы
ушли в инструменты и что они вернули. Нужен запущенный Phoenix (`scripts/catix.sh up`); без него тесты идут как обычно, только без ссылок.

| Файл                                       | Что проверяет                                                                                                                                        | Чем      |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| `tests/test_answers.py`                    | точная дата и аудитория, относительные даты («послезавтра»), обоснованность ответа, отсутствие выдуманного расписания и выдуманной группы, язык ответа                   | DeepEval |
| `tests/test_indirect_injection.py`         | инъекции через сообщения чата (принудительное слово, раскрытие промпта, подброшенная ссылка, просьба выполнить SQL, реклама «в каждом ответе») и прямые попытки: вытащить промпт, добавить рекламу | DeepEval |
| `tests/test_change_detection.py`           | отличает перенос, отмену и анонс от вопросов, слухов и шуток (16 примеров)                                                                           | DeepEval |
| `tests/test_redteam.py` (маркер `redteam`) | атаки на утечку промпта, перехват управления и SQL-инъекции, 5 техник: инъекция, Base64, ROT13, мультиязычная, ролевая                               | DeepTeam |

- **Временный чат.** Тесты создают в базе чат `tests: synthetic chat` (id `-999000999`) с известными фактами и тремя подброшенными инструкциями и удаляют его в конце. Даты считаются от сегодняшнего дня, реальные чаты не затрагиваются.
- **Судья и атакующий** это та же локальная модель, что отвечает пользователям: «тест прошёл» значит «эта модель не смогла сломать эту модель». Маленькая модель как судья ошибается, поэтому точные факты (дата, аудитория, язык, отсутствие запрещённых строк) проверяются кодом без модели, а упавший `Faithfulness` (единственный тест с судьёй) стоит читать глазами: `GEval` убран, он путал верные ответы.
- **Телеметрия DeepEval и DeepTeam отключена** (`tests/helpers.py` выставляет `*_TELEMETRY_OPT_OUT` до импорта): промпты и ответы не уходят на сторонние серверы.
- **Почему долго.** Модель обрабатывает один запрос за раз, поэтому тесты идут по очереди и делят модель с работающими ботами. На время прогона можно остановить приложения (`scripts/catix.sh down`): атаки пройдут заметно быстрее.
- Скрипты оценки качества, которые не тесты (сравнение вариантов поиска и работы с датами), лежат в `experiments/`: `uv run python experiments/eval_search.py` и другие.

## Безопасность и приватность

- Модель не пишет SQL: тулы чатов (`search_chats`, `read_chats`) сами ограничивают выдачу чатами, разрешёнными этому пользователю, а её слова уходят в запрос параметрами. Роль `ctx_reader` и представления `visible.*` остались от прежнего тула `query_db` (SQL модели) и агентом больше не используются.
- Ручной выбор учебной группы на сайте — **удобство, а не подтверждение принадлежности**: доступ к защищённым источникам требует проверки группы через InNoHassle.
- Бот и userbot сохраняют сообщения только настроенных источников; участников нужно предупредить о хранении и выбранной аудитории. Для MAX используйте отдельный разрешённый аккаунт и подтверждение в Telegram либо одобренную модератором заявку сайта с явной аудиторией; личные диалоги не индексируются.
- Секреты только в `.env` (не в git). Личный календарь открывается только с токеном InNoHassle его владельца.

## HTTP API (`catix-api`)

cAtIx заменил сервис поиска InNoHassle и отвечает по его прежним путям и схемам; авторизация та же (`Authorization: Bearer <токен InNoHassle>`). Документация: `/docs`.

| Путь | Что делает |
|---|---|
| `GET /search/search` | карточки-источники из вики (`sources` фильтрует по типу; документы университета и чужие сайты приходят карточками `eduwiki` со своими `breadcrumbs`) |
| `POST /search/search/{id}/feedback` | оценка карточки (хранится в памяти процесса) |
| `POST /ask/` | вопрос агенту, `chat_id` ведёт диалог; без него или с неизвестным `chat_id` начинается новый чат. Пока агент отвечает на первый вопрос, модель отдельным коротким вызовом называет чат по этому вопросу (`agent/titles.py`, 2–6 слов на языке вопроса; ответ ждёт название не дольше 5 с); до тех пор и если вызов не удался, название — сам вопрос, и следующий вопрос пробует снова. Диалоги хранятся в Postgres и переживают перезапуск: память агента — в таблицах LangGraph (`AsyncPostgresSaver`, поток `api:<chat_id>`; `catix-api` создаёт их при старте), ответы, какими их получил клиент, — в `api_chats` и `api_answers`. Отменённый или упавший вопрос не остаётся ни в памяти агента, ни в истории: следующий продолжает с последнего ответа. Вопросы одного клиента отвечаются по одному, в порядке прихода (FIFO), в каком бы чате они ни были; вопросы разных клиентов идут параллельно, до `AGENT_PARALLEL_QUESTIONS` сразу. В ответе `calendar_events`: ближайшие события, которые называет ответ (экзамен, дедлайн), для кнопок «➕ В мой календарь»; их находит ещё один короткий вызов модели, только если в ответе есть дата |
| `POST /ask/{id}/feedback` | 👍/👎 на ответ (`feedback`: `like` / `dislike`, в теле необязательный `comment` до 2000 символов — что понравилось или нет): аннотация `user-feedback` к трассе ответа в Phoenix (комментарий — её `explanation`); повторная оценка пользователя заменяет прежнюю. `ask_query_id` у ответа есть, только когда включена трассировка; оценка с комментарием хранится при ответе и видна в истории чата |
| `GET /ask/chats` | чаты пользователя с ассистентом (только с ответами), сначала последний отвеченный, до 100 |
| `GET /ask/chats/{chat_id}` | чат пользователя: вопросы и ответы по порядку, какими их дал `POST /ask/` (с источниками, `calendar_events` и оценкой пользователя: `feedback`, `feedback_comment`; `messages` пуст), чтобы вернуться к нему и продолжить с его `chat_id`; чужой или неизвестный — `404` |
| `PATCH /ask/chats/{chat_id}` | переименование чата пользователем (`{"title": ...}`, до 200 символов); после этого модель название не меняет |
| `DELETE /ask/chats/{chat_id}` | удаление чата пользователем: его вопросы и ответы с оценками и память агента о нём (поток `api:<chat_id>`). Идущий или ждущий вопрос этого чата сначала отменяется (`409` / `cancelled`); вопрос с этим `chat_id` после удаления начинает новый чат. Трассы в Phoenix и события, добавленные в календарь, остаются; чужой или неизвестный — `404` |
| `POST /ask/{chat_id}/cancel` | отмена работы агента в чате: идущего вопроса и ждущих своей очереди вопросов этого чата. Их запросы завершаются `409` (в `/ask/stream` событием `cancelled`), диалог остаётся таким, каким был до отменённых вопросов |
| `POST /act/` | заглушка: действий в сервисах InNoHassle в cAtIx нет |
| `GET /sites` | доверенные настроенные сайты (`name`, `url`, `about`) из каталога `sites.SITES` |
| `POST /{section}/parse` | заявка на обновление источника для собственного прогона вики (autopilot): `wiki` / `eduwiki`, `sites` / `resources`; прежние `hotel` и `campuslife` выбирают соответствующий сайт |
| `GET /parse/{id}` | состояние заявки: `queued`, `running`, `done` (`outcome`: `committed`, `review`, `unchanged`) или `failed` |
| `GET /users/my-calendar.ics` | личный календарь пользователя (iCalendar): события, добавленные кнопкой «➕ В мой календарь» или агентом на сайте после подтверждения. Календарь принадлежит аккаунту InNoHassle (`uid` токена; email не нужен). Бот узнаёт аккаунт по Telegram id через `INNOHASSLE_SERVICE_TOKEN`; события, добавленные в боте, пока аккаунт не был известен, переходят в него, как только он найден (или токен аккаунта покажет этот `telegram_id`) |
| `POST /users/my-calendar/events/{proposal_id}` | кнопка под ответом: событие из `calendar_events` (его `id`) в календарь пользователя. Предложение живёт 48 часов, потом `404`; повторное нажатие не создаёт второе событие |

`POST /ask/stream` и `POST /ask/{chat_id}/decision/stream` передают `answer` с полным текстом ответа на данный момент, не с дельтой. Помимо финального ответа супервизора, поток может показывать финальный ответ единственного помощника без дополнительного переписывания: только из явно завершающего вызова модели без инструментов, после поиска и проверки свежих ссылок. Промежуточные черновики и рассуждения помощников не передаются. Ненумерованные внутренние ссылки скрыты; если частичный ответ отозван и требуется синтез, `answer` с `text: ""` очищает его перед продолжением. Итоговые источники и результат приходят в прежнем `done`; события статуса, ошибки и отмены не меняются.
Частичные ответы помощника объединяются по завершённым предложениям: незавершённые ссылки и атрибуции не показываются до проверки. Это не искусственная печать готового ответа: обновления приходят во время генерации. Одно короткое предложение или отчёт, завершённый без заранее запрещённых инструментов, может по-прежнему появиться только целиком.

Парсинг требует того же Bearer-токена. API сам в вики не пишет (в `docker-compose.prod.yml` её checkout смонтирован
только для чтения): он ставит заявку в очередь в Redis (`src/catix/wiki/parse_requests.py`) и сразу отвечает `202`
с заявкой. `catix-wiki autopilot` берёт заявку, спрашивает названный источник и прогоняет то, что пришло, через
обычную цепочку: сборка, агент вики, проверки (lint, карточки, поиск, ответы), коммит в ветку `wiki` и push.
Если проверка не прошла, изменения уходят в `wiki-review/<время>` и ждут человека (`outcome: review`).
Поиск на сервере получает изменения, когда `scripts/wiki-pull.sh` подтягивает ветку.

`POST /sites/parse?sites=hotel&sites=campuslife` — это `catix-wiki autopilot --site hotel --site campuslife`:
источник `sites` только для этих сайтов, то есть их документы (HEAD), страницы и документы, на которые они ссылаются
(только текстовый слой, сканы ждут OCR). У других сайтов, на которые они ведут, читаются только страницы, которых в вики
ещё нет. Без `sites` берётся весь доверенный каталог `GET /sites`. Произвольные URL
и неизвестные имена получают `400`, а имя, пропавшее из каталога до прогона, прогон пропускает. `POST /eduwiki/parse` —
источник `eduwiki` (страницы, у которых сменилась ревизия). Заявки, которые ждут вместе, обслуживает один прогон
(сайты разных заявок читаются вместе). Та же заявка, пока она ждёт, ставится один раз: повторный запрос возвращает её.
`autopilot --loop` просыпается ради заявки за полминуты; если идёт другой прогон, заявка ждёт, пока он закончится.

`parsing_is_needed=false` ни один источник не спрашивает: прогон собирает и проверяет то, что уже лежит в данных.
`indexing_is_needed` оставлен для совместимости и ничего не меняет: прогон индексирует всегда, а индекс сервера следует
за веткой. Оба `false` дают `400`. Без `REDIS_URL` или с недоступным Redis ответ `503`. Ответ и `GET /parse/{id}`
содержат `id`, `section`, `source`, `sites`, `parsing`, `status`, `outcome`, `result` (строку прогона, например
`committed 1a2b3c: 12 files and pushed`), а также `created_at`, `started_at` и `finished_at`. Заявка, чей источник
упал, получает `failed`. Если прогон умер, заявку берёт следующий; после трёх таких попыток она получает `failed`.
Готовые заявки хранятся 30 дней. `moodle`, `clubs`, `maps`, `residents` по-прежнему возвращают `410`:
для сайта выбирайте его имя через `/sites/parse`.

Настройки: `API_HOST`, `API_PORT`, `API_ROOT_PATH`, `API_CORS_ALLOW_ORIGIN_REGEX`. Запуск: `catix-api` (в `docker-compose.prod.yml` сервис `api`).

## Текст на изображениях в чатах

`tguserbot listen`, `tgbot` и `maxuserbot listen` распознают изображения в сохраняемых сообщениях для поиска
агентом InNoHassle. Это фоновая индексация, не новый режим ответа в личке бота. Подпись, автор,
дата и ссылка на сообщение сохраняются сразу; буквальная расшифровка добавляется к тому же
сообщению с пометкой OCR. Исходная подпись хранится отдельно. Для Telegram действуют прежние
настройки `/listen` и ограничения тем; личные вопросы боту не становятся источниками поиска.

Распознавание использует только локальный Tesseract с языками `rus+eng`, без HTTP, vLLM fallback
или переключения моделей. В Docker зависимости включены; на хосте обязательны `tesseract`
и обе языковые модели (`tesseract --list-langs`). OCR вложений агента и wiki не меняется.
Постоянная очередь в Postgres ограничивает работу одним сообщением одновременно для всех трёх
клиентов и продолжает её после перезапуска. Редактирование подписи или замена картинки
инвалидируют прежнюю расшифровку; запоздалый результат не применяется.
Текст после OCR автоматически попадает в очередь пересчёта эмбеддинга и в полнотекстовый индекс.

Поддерживаются статические JPEG, PNG и WebP; не стикеры, GIF, видео или PDF. Ограничения:
10 MiB и 20 млн пикселей на изображение, до 10 изображений на сообщение, длинная сторона
до 2048 пикселей, до 180 секунд на всё сообщение. На изображение — до 10 секунд Tesseract,
256 KiB TSV и один OpenMP-поток. Принимается только текст со средней уверенностью ≥90,
каждым словом ≥80 и каждым словом с цифрой ≥90. Неуверенная, пустая, слишком длинная картинка,
timeout или превышение TSV пропускаются целиком без retry: подпись сохраняется без OCR-маркера;
у альбома остаются исходные номера уверенных изображений. Эвристика не гарантирует отсутствие
ошибок или пропусков блоков на реальных афишах; даты и текст автоматически не исправляются.
Отсутствие Tesseract/языков, ненулевой exit, неверные UTF-8/TSV или stderr >16 KiB — техническая
ошибка: сообщение не получает частичный OCR, после трёх попыток задача остаётся `failed`.

Перед запуском обновлённых клиентов примените схему `catix-db init`. Уже сохранённая история
сама не скачивается повторно ради OCR; новые сообщения и изображения, поступившие при обычной
синхронизации/загрузке истории, ставятся в очередь. `tguserbot sync` только ставит задачи,
а обрабатывает их работающий `tguserbot listen`.

## Структура репозитория

```
src/catix/
  agent/       агент: супервизор и помощники (core, roles), экран (guardrail), инструменты, SQL для модели, трассировка

  tguserbot/   userbot (Telethon)
  maxuserbot/  пассивный пользовательский клиент MAX (PyMax), каталог, inbox, история и OCR
  worker/      воркер: embedder, changes (расписание), health (алерты), app
  ingest/      запись сообщений: writer, noise, публикация в Redis, очередь и OCR изображений
  db/          пул, хранение и поиск (store), схема и CLI (init)
  api/         HTTP API прежнего сервиса поиска (app, search, ask, parsers) и личный календарь (users)

  groups.py, admins.py, userbot_config.py   учебные группы, админы, выбор чатов
db/schema.sql  схема Postgres (применяется `catix-db init`, повторяема)
scripts/       catix.sh (запуск для разработки), backup.sh
tests/         тесты на DeepEval и DeepTeam (pytest)
experiments/   скрипты оценки качества поиска и дат
```
